## Разделы основной спецификации

Существующие номера разделов сохраняются внутри отдельных файлов: [§1–2](foundation.md), [§3 — 19 паспортов](skills/index.md), [§4](data-model.md), [§5](result-formats.md), [§6 и историческая часть §8](history.md), [§7](acceptance.md), [§8.1](workflows.md), [§9–10](technical-references.md), [§11](defaults.md), [§12](governance.md). Для старых ссылок на единый файл действует [точка перехода](Obsidian_Claude_Skills_Spec.md), а неизменённая копия v0.7 лежит в [архиве](Obsidian_Claude_Skills_Spec_v0.7-archive.md). Открытые вопросы §2–3 сохранены для трассировки; принятые ответы находятся в §11 и новых `REQ-*`.

Новые нормативные положения добавляются в файл отвечающего skill либо в общий файл соответствующего домена (`foundation`, `data-model`, `defaults`, `workflows`, `governance`). Один нормативный текст каждого требования; индексы и карты содержат ссылки, а не копии. При переносе между файлами сохранить ID и обновить входной индекс и кросс ссылки; архив не редактировать как актуальную спецификацию. Причины структуры зафиксированы в [ADR-0005](../adr/ADR-0005-modular-spec.md).

## Пространства идентификаторов

| Тип | Формат | Пример | Правило |
|---|---|---|---|
| Старый вопрос/правило | `LEG-<старый ID>` в реестре; в тексте старый ID остаётся | `LEG-S1` → §3.1 / §11 S1 | Заморозить; не выдавать новым требованиям. Префикс `LEG-` снимает коллизию с `[S1]` из списка технических источников. |
| Новое требование | `REQ-<DOMAIN>-NNNN` | `REQ-DOC-0001` | Уникальный постоянный код в общем реестре, 4 цифры, счётчик отдельно по домену, без переиспользования. |
| User story | `US-NNN` | `US-001` | Один пользовательский результат, может вести к нескольким требованиям. |
| Критерий приёмки нового требования | `AC-<REQ-ID>-NN` | `AC-REQ-DOC-0001-01` | Локален для требования; доработка добавляет новый критерий, не перенумеровывает старые. |
| Архитектурное решение | `ADR-NNNN` | `ADR-0001` | Независимо от требований; ссылка на `REQ`/`LEG`/`US`. |

Домены: `FND` (основа/данные), `RET` (поиск), `KNO` (создание знаний), `NAV` (MOC/HUB), `QRY` (запросы), `WRK` (workflow), `INT` (интеграции), `QLT` (проверка), `DOC` (управление спецификацией). Новый домен допустим после записи его значения в этот файл и реестр. Коды не содержат номер версии, имя skill или номер раздела: перенос файла не меняет ID.

## Как добавлять требование

1. Найти связанную user story и уже имеющиеся `LEG-*`/`REQ-*`; не регистрировать дубликат. Если потребность новая, создать `US-NNN` с ролью, целью, ценностью и наблюдаемым исходом.
2. Назначить следующий свободный номер домена по [реестру](requirements-registry.md). Не переиспользовать даже удалённый/отклонённый код. Новые пункты в старом блоке S/C/R и т. п. **не получают** `S7`, `C7` и т. п.
3. Записать атомарное проверяемое `Система должна…`, область действия/исключения, статус (`Proposed`, `Accepted`, `Implemented`, `Deprecated`, `Superseded`), ссылку на story и родственные legacy IDs. `Implemented` ставить только после проверки кода.
4. Присвоить критериям приёмки собственные коды, связать с тестами или ручной проверкой. Определить, нужен ли ADR для значимого технического выбора.
5. Обновить соответствующий нормативный файл и реестр в одной задаче; затем карты, алгоритмы, user stories и ADR index по затронутым ссылкам. Сохранять формулировку исходного требования; уточнение писать как новое требование с `refines`/`supersedes`.

## Изменения и конфликт

`Proposed` ещё не нормативно; `Accepted` задаёт поведение; `Implemented` подтверждено проверкой. Отменённый ID остаётся записью со статусом `Deprecated`/`Superseded by REQ-...`. При конфликте нового требования с legacy зафиксировать `supersedes` и явно обновить основной нормативный текст. Новое указание пользователя имеет приоритет; не прятать несовместимое требование в ADR или карту.
