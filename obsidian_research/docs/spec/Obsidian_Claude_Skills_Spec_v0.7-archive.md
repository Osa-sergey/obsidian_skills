# Набор Claude Skills для тематического Obsidian Vault

Статус: спецификация для разработки, версия 0.7.
Дата: 2026-09-29.

Это описание будущего набора скиллов, а не установленная интеграция. Содержимое vault и установленные плагины не проверялись. Исторические вопросы и предварительные предложения в разделах 2–8 сохранены для трассировки; принятые рабочие дефолты приведены в §11. Правила кодирования новых требований и user stories — в §12.

## 1. Цель и границы

Превратить тематический vault в рабочую базу знаний, с которой Claude может последовательно выполнять поиск, собирать связанный контекст, проводить исследование и готовить согласованный набор новых статей, предложений по обновлению существующих материалов и навигационных страниц.

Под «статьёй» далее понимается Markdown-заметка в Obsidian. Под «источником» — как существующая заметка, так и исходная публикация, документ, запись или другой материал, на котором основано утверждение.

### Подтверждённые пользователем требования

- Искать заметки по названию через Omnisearch.
- Собирать списки связанных заметок по теме с задаваемой глубиной контекста.
- На основе исследования формировать новые статьи и предложения по изменению существующих статей близкой тематики.
- Сохранять ссылки на исходные данные и на статьи в vault.
- Собирать статьи в MOC; организовать сами MOC иерархически.
- В каждом MOC явно указывать ракурс рассмотрения темы отдельным полем.
- Представлять HUB как удобный для просмотра Canvas, объединяющий MOC и отдельные статьи, с этапами работы, изучения процесса или информации.
- Проставлять полезные перекрёстные ссылки и находить связи между Markdown-файлами.
- Формировать метаполя в YAML-заголовке, включая теги для поиска.
- Разделить функциональность на набор скиллов и уточнить вопросы по каждому.
- Поддержать два режима работы с базой знаний: `narrow` для точечных вопросов с минимальным контекстом и `deep` для исследования, синтеза и встраивания новых знаний.
- Добавить семантический поиск по иерархическому RAPTOR-представлению, построенному с учётом структуры Markdown: статья → раздел → подраздел → абзацы/чанки.
- Читать отдельные абзацы, разделы и при необходимости их подразделы без обязательного чтения статьи целиком.
- Объединять Omnisearch, поиск по терминам, RAPTOR, Dataview/Bases и граф связей в единый управляемый retrieval-процесс.
- Для каждого MOC хранить краткое summary и список основных терминов, используемых в карте.
- Для каждого HUB использовать обязательную пару: отдельная Markdown-заметка с описанием и связанный Canvas-файл.
- Новые статьи писать максимально структурированно: одна смысловая единица на абзац, явные заголовки/подзаголовки, устойчивые границы разделов для адресного чтения и RAPTOR-индексации.
- Поддерживать Obsidian Callouts вида `> [!TYPE]` для выделения определений, выводов, предупреждений, примеров, вопросов, источников и другой важной информации.
- Сохранять часто используемые Dataview/Bases-запросы как переиспользуемые файлы/представления внутри vault, снабжать их описанием назначения, условиями применения и ссылками из каталога запросов.

|---|---|---|---|

| 2 | `obsidian-context` | Обход существующих ссылок и графовых связей | Контекст по уровням, маршруты и причины отбора |

Ключевой архитектурный принцип версии 0.6: специализированные поисковые адаптеры не отвечают на вопрос пользователя напрямую; они возвращают кандидатов и provenance, а `obsidian-retrieve` формирует общий retrieval-план и бюджет контекста.

## 2. Общая техническая основа

### 2.1. Скиллы и доступ к данным

Скилл определяет, как Claude выполняет задачу. Доступ к Obsidian обеспечивается отдельно: подключёнными инструментами, MCP, API или разрешённым чтением файлов.

Omnisearch документирует локальный HTTP-сервер для внешних запросов; его нужно включить. Он ранжирует результаты с учётом текста, имени файла и заголовков, поэтому нельзя автоматически считать все результаты поиском только по названию. Для режима поиска по названию адаптер должен проверить имя/заголовок найденной заметки и применить согласованные правила отбора. [S2]

Для чтения и изменения файлов можно рассмотреть Local REST API с MCP либо файловый доступ в локальном Claude Code. Local REST API документирует чтение, создание и изменение заметок, включая адресное обновление разделов и свойств. Поддержку именно Omnisearch в выбранном подключении следует проверить отдельно: наличие обычного поиска в MCP её не гарантирует. [S3]

Для первой реализации предлагается ориентироваться на локальный Claude Code, но это требует ответа на G1. В Claude Code скилл оформляется папкой с `SKILL.md`; описание помогает автоматическому выбору, а отдельный скилл можно вызвать по имени. Проектные скиллы размещаются в `.claude/skills/<имя>/SKILL.md`. [S1]

### 2.2. Общий профиль vault

Один согласованный профиль должен хранить:

- идентификатор vault, способ подключения и доступные возможности;
- разрешённые и исключённые папки;
- схему типов заметок, метаданных, тегов и алиасов;
- правила имён файлов и внутренних ссылок;
- обязательные префиксы навигационных файлов: `MOC_<Название>.md` для MOC и `HUB_<Название>.md` для Markdown-описания HUB; связанный Canvas именуется `HUB_<Название>.canvas`;
- места для новых статей, источников, MOC, HUB и исследовательских отчётов;
- лимиты поиска, обхода графа и объёма чтения;
- допустимые действия: отчёт, создание черновиков, применение выбранных изменений;
- правила обработки существующих пользовательских разделов.

Не следует копировать этот профиль целиком во все скиллы. Доступ к нему должен быть определён одинаково для всего набора. Ключи подключения хранить в конфигурации инструментов, а не в текстах статей.

### 2.3. Обязательные правила результата

1. Прочитать материал перед его содержательным использованием. Поисковый фрагмент служит для отбора, а не заменяет источник.
2. Различать обнаруженную заметку, прочитанный материал и материал, использованный для вывода.
3. Давать для существенного вывода ссылку на конкретное основание. Общего списка источников в конце недостаточно для спорных или точных утверждений.
4. Отделять факты источника, интерпретацию автора заметки и новый вывод Claude.
5. Не представлять ссылку на непрочитанный первоисточник как проверенное подтверждение. Если доступна только вторичная заметка, явно указывать это.
6. Разрешать внутренние ссылки до конкретного пути. Совпадение имён в разных папках и алиасы требуют проверки.
7. Не смешивать существующие ссылки и предлагаемые смысловые связи.
8. Искать существующее покрытие темы перед созданием статьи.
9. Для старых статей готовить адресные предложения изменений. Применять их только в рамках отдельного запроса на применение или заранее согласованного режима.
10. Сохранять чужие метаполя, авторские формулировки, ручные комментарии и разделы вне согласованной правки.
11. Повторный запуск на неизменившихся данных не должен плодить статьи, ссылки, теги и одинаковые предложения.
12. Перед записью сверять актуальную версию файла с прочитанной. При расхождении пересобрать правку, сохранив новые пользовательские изменения.

### 2.4. Уточнённая модель: статьи, иерархические MOC и Canvas HUB

Уточнение пользователя от 2026-09-28 фиксирует три роли:

| Сущность | Назначение | Форма |
|---|---|---|
| Статья | Изложение конкретного материала; включается в MOC | Markdown-заметка |
| MOC | Подборка статей и дочерних MOC по теме в явно указанном ракурсе | Markdown-заметка с метаданными и аннотированными ссылками |
| HUB | Маршрут работы/изучения с машинно-читаемым описанием и визуальным представлением | Обязательная пара `HUB_<Название>.md` + `HUB_<Название>.canvas` |

Иерархия MOC, ракурс и маршрут HUB — разные отношения. Уровень MOC показывает положение в структуре темы. Ракурс объясняет, с какой стороны рассматривается тема. Положение на Canvas показывает роль материала в конкретном рабочем или учебном маршруте.

**Предлагаемые правила, требующие согласования деталей:**

- Для каждого MOC обязательны тема и явно заполненное поле `perspective` («ракурс»). Поле `perspective_question` поясняет, на какой вопрос отвечает этот взгляд. Например: `perspective: operations`, `perspective_question: Как поддерживать актуальность и надёжность RAG в эксплуатации?`.
- Возможные ракурсы: теория, архитектура, реализация, эксплуатация, оценка качества. Аудитория, сложность и позиция в процессе задаются отдельно: они не заменяют ракурс.
- Одна тема может иметь несколько MOC с разными ракурсами. Это разные подборки и объяснения, а не автоматически дублирующиеся заметки.
- Статью можно включать в несколько MOC ссылками, без копирования текста. Прямое включение статьи в HUB не отменяет её принадлежность MOC. Множественная принадлежность предлагается как базовое правило, окончательно уточняется в O9.
- Родительство хранить в `parent_mocs`. Корневой MOC имеет пустой список. До решения O7 предлагается один родитель; формат списка позволяет позже разрешить несколько родителей без смены типа свойства.
- Иерархия не допускает циклов. При нескольких родителях она становится направленным ациклическим графом. Перекрёстные тематические ссылки не считать отношением родительства.
- Дочерние MOC определять по `parent_mocs`; их аннотированный список в тексте родителя согласовывать с этими полями. Не хранить независимые несогласованные списки родителей и детей.
- В каждом MOC хранить ракурс явно, даже если он совпадает с родительским. Если дочерняя карта меняет ракурс, показывать это в её названии/аннотации и в переходе от родителя.
- Уровень иерархии вычислять по связям. При нескольких родителях указывать путь, относительно которого рассчитан уровень. Не смешивать его с глубиной обхода контекста и номером этапа HUB.
- Каждая итоговая статья должна иметь хотя бы один целевой MOC; для новых черновиков допустима запланированная принадлежность с явным статусом, пока MOC не создан.
- HUB выбирает необходимые материалы из разных уровней и ракурсов. Вся иерархия MOC не обязана помещаться на один Canvas.

**Устройство HUB:** визуальные группы представляют этапы. В каждой группе — название, цель, карточки нужных MOC/статей и ожидаемый результат этапа. Стрелки с подписями различают «следующий этап», «предпосылка», «альтернатива», «возврат на доработку». Порядок, зависимости и ветвления должны читаться без открытия всех карточек.

Пример: HUB «Разработка RAG» объединяет этапы постановки задачи, подготовки данных, реализации, оценки и эксплуатации. На этапе подготовки данных могут стоять MOC «Индексация — реализация» и отдельная статья «Чек-лист качества входных документов». На этапе оценки — MOC «RAG — оценка качества» и статья «Набор тестовых вопросов». Пример не задаёт обязательную структуру всех HUB.

Нативный Obsidian Canvas хранится в формате JSON Canvas и поддерживает карточки файлов, текст, группы и связи. Предлагается использовать карточки файлов для MOC и статей, а текстовые карточки — для кратких пояснений и легенды. [S6][S7]

Файл `.canvas` не является Markdown-заметкой с YAML. Поэтому для каждого HUB обязательна сопроводительная заметка `HUB_<Название>.md` с метаданными, summary, назначением, этапами, основными терминами и ссылкой на `HUB_<Название>.canvas`. Markdown-файл является машинно-читаемым описанием HUB и основной точкой поиска; Canvas отвечает за визуальный маршрут. Метаданные нельзя добавлять YAML-заголовком в JSON-файл. Линии Canvas и родительство MOC не считать автоматически одинаковыми связями. Текстовые карточки Canvas не появляются в Backlinks как самостоятельные заметки. [S6][S7]


### 2.5. Правила именования MOC и HUB

Для навигационных сущностей используются обязательные файловые префиксы, отделённые символом `_`:

- MOC: `MOC_<Название>.md`;
- Markdown-описание HUB: `HUB_<Название>.md`;
- Canvas HUB: `HUB_<Название>.canvas`.

Примеры:

```text
Maps/MOC_RAG - Индексация.md
Maps/MOC_GraphRAG - Эксплуатация.md
Hubs/HUB_Разработка RAG.md
Hubs/HUB_Разработка RAG.canvas
```

Префикс является частью имени файла и используется для быстрого распознавания типа заметки средствами файлового поиска, Omnisearch и автоматических skills. Поле `type` в YAML при этом остаётся обязательным источником семантического типа и не заменяется соглашением об имени файла.

При создании, переименовании и поиске MOC/HUB skills должны:

1. сохранять соответствующий префикс;
2. не создавать варианты `MOC - ...`, `HUB - ...` или файлы без префикса;
3. проверять, что Markdown-файл HUB и его Canvas имеют одинаковую базовую часть имени;
4. обновлять внутренние ссылки при согласованном переименовании;
5. не считать произвольный файл с похожим названием MOC/HUB без проверки YAML `type`.

### 2.6. Два режима retrieval и иерархия RAPTOR

Система должна поддерживать два явно различимых режима.

**`narrow` — точечный ответ.** Используется для конкретного вопроса, поиска определения, алгоритма, факта, места в тексте или короткого списка. Цель — получить минимальный достаточный evidence set. По умолчанию нельзя читать статью целиком, если достаточно summary, конкретного раздела, подраздела или нескольких абзацев.

**`deep` — исследование и развитие базы.** Используется для обзора темы, сравнения подходов, поиска пробелов и противоречий, deep research, подготовки новых статей и встраивания новой информации. Режим допускает более широкий candidate set, несколько итераций поиска, обход MOC/графа и расширение выбранных RAPTOR-ветвей.

RAPTOR строится с учётом естественной структуры Markdown:

```text
article
└── section (H1/H2)
    └── subsection (H2/H3/...)
        └── paragraph group
            └── atomic paragraph/chunk
```

Для каждого индексируемого узла хранить как минимум: `path`, `heading_path`, `node_level`, `parent_id`, диапазон строк/абзацев, content hash, summary, embedding и список child IDs. Границы заголовков должны иметь приоритет над слепым token chunking. Если раздел слишком велик, он делится по абзацам/логическим блокам с сохранением обратной ссылки на исходный heading.

Прогрессивное раскрытие контекста:

1. metadata/MOC/HUB summary;
2. RAPTOR summaries верхнего уровня;
3. выбранные разделы и подразделы;
4. конкретные абзацы;
5. полная статья — только если без неё невозможно корректно выполнить задачу.

`obsidian-fragment-reader` является обязательным downstream-инструментом `obsidian-semantic-search`: семантический поиск возвращает адрес узла, reader читает исходный фрагмент и при необходимости раскрывает только его дочерние подразделы.

### 2.7. Hybrid retrieval и бюджет контекста

`obsidian-retrieve` объединяет независимые механизмы:

- Omnisearch — названия, текст и нечёткие совпадения;
- term search — точные термины, названия технологий, сущности и устойчивые фразы;
- RAPTOR — семантическое соответствие на уровнях article/section/subsection/chunk;
- Dataview/Bases — структурированные фильтры по свойствам, ссылкам, статусам и датам;
- MOC/HUB — навигационная близость, ракурс и место в тематической структуре;
- backlinks/outlinks — существующий граф заметок.

Dataview/Bases предпочтительно использовать как pre-filter, если вопрос содержит структурные ограничения. Например, сначала выбрать статьи `type=article`, `published>=2025`, относящиеся к RAG, и только затем выполнять RAPTOR по полученному scope.

Каждый запрос получает `context_budget`, например:

```yaml
mode: narrow
max_tokens: 6000
allocation:
  discovery: 800
  summaries: 1200
  evidence: 3200
  reserve: 800
```

Число файлов не является достаточным ограничителем. Оркестратор должен оценивать стоимость чтения summary/section/article и расширять контекст постепенно.


### Вопросы об окружении

- **G1 — критично.** Где будут запускаться скиллы: Claude Code локально, Claude Desktop/Cowork, веб-версия Claude или несколько сред?
- **G2 — критично.** Как подключён vault? Какие версии Obsidian, Omnisearch и инструменты доступа уже есть? Можно ли добавить недостающее подключение?
- **G3.** Один vault или несколько? Каков примерный размер: число заметок, общий объём, доля больших документов и вложений?
- **G4.** Какие плагины и соглашения нужно поддержать: Dataview/DataviewJS, Templater, Bases, собственные шаблоны? Какие из них обязательны?
- **G5 — критично.** Какие папки разрешено читать и куда можно создавать новые материалы? Какие папки исключить?
- **G6 — критично.** Какие действия разрешены сразу: только выдача черновиков, создание новых файлов, применение заранее описанных типов изменений? Предложения по существующим статьям считаем обязательным отдельным результатом.
- **G7.** Можно ли прислать 3–5 характерных заметок, один текущий MOC/HUB и дерево основных папок? Это позволит сохранить стиль и существующие соглашения.

## 3. Описания скиллов и вопросы

### 3.1. `obsidian-search` — поиск заметок

**Кандидат для `description`:**

> Находить заметки Obsidian через Omnisearch по названию, части названия и согласованным вариантам термина. Использовать, когда пользователь просит найти статью в vault, подобрать исходные заметки по теме или проверить, существует ли уже материал. Возвращать проверенные пути, ссылки, краткий контекст и основание включения.

**Вход:** запрос, режим поиска, папки, фильтры, лимит результатов.

**Обработка:** выполнить запрос в Omnisearch; проверить доступность результатов; нормализовать пути; объединить дубликаты выдачи; различить совпадения в имени файла, свойстве `title`, aliases, заголовках и тексте. Последние варианты включать только в разрешённых режимах. Результаты Omnisearch считать ранжированием, а не вероятностью истинности.

**Выход:** таблица `заметка → путь → тип совпадения → краткое пояснение → ссылка`. Отдельно указать использованные запросы, недоступные результаты и ограничения поиска. Резервный файловый поиск, если он разрешён, явно обозначить.

**Пример запроса:** «Найди заметки по GraphRAG и обновлению графа, сначала по названиям».

**Критерий готовности:** каждая ссылка соответствует реально найденному файлу; точные совпадения отличимы от расширенного поиска.

**Вопросы:**

1. **S1 — критично.** Что означает «название»: имя `.md`, первый H1, YAML `title`, aliases или сочетание? Что приоритетнее при расхождении?
2. **S2.** Нужен строго поиск по названию или поиск в тексте при недостатке совпадений?
3. **S3.** Нужны русские/английские варианты, сокращения и исправление опечаток? Например, RAG / retrieval augmented generation / поиск с генерацией.
4. **S4.** Какие фильтры обязательны: папка, теги, тип заметки, дата, статус, язык? Фильтры можно применять после Omnisearch, если выбранный интерфейс их не поддерживает.
5. **S5.** Сколько результатов показывать по умолчанию и нужны ли краткие аннотации уже на этапе поиска?
6. **S6.** Что делать при недоступности Omnisearch: остановить поиск с объяснением или использовать явно обозначенный резервный способ?

### 3.2. `obsidian-context` — связанный контекст с глубиной

**Кандидат для `description`:**

> Собирать тематический контекст из найденных или указанных заметок Obsidian, обходя существующие внутренние ссылки до заданной глубины. Использовать, когда нужно изучить окружение статьи, получить список связанных материалов по уровням или подготовить ограниченный пакет источников для исследования. Показывать маршруты связи и причины отбора.

**Вход:** исходные заметки, тема, глубина, направления обхода, разрешённые типы связей, лимиты; при работе с MOC — фильтр ракурса и глубина иерархии отдельно; при работе с HUB — выбранный маршрут и этапы.

**Определение глубины:** уровень 0 — исходные заметки; уровень 1 — соседи по разрешённым связям; уровень 2 — их соседи. Для нескольких исходных заметок указывать минимальную глубину и хотя бы один маршрут. Это число переходов по графу, а не глубина папок или заголовков.

**Обработка:** обходить исходящие ссылки и/или обратные ссылки; предотвращать циклы; читать релевантные разделы; отдельно учитывать встраивания, ссылки на заголовки и блоки. Широкие HUB и общие MOC не должны бесконтрольно расширять контекст. Различать родительство MOC, принадлежность статьи MOC, смысловые кросс-ссылки и переходы маршрута Canvas. Рёбра Canvas читать отдельно, если выбранный доступ поддерживает `.canvas`; не восстанавливать их предположительно по обратным ссылкам заметок. Применять пределы числа заметок, соседей и объёма текста, фиксируя причины остановки.

**Выход:** список по уровням и компактный контекст. Для каждой заметки: путь, глубина, предшественник, направление связи, раздел, причина релевантности, статус чтения. Если структура показана деревом, не терять повторные связи графа: указывать их отдельно.

**Пример запроса:** «Собери окружение статьи об инкрементальном GraphRAG на глубину 2, включая обратные ссылки».

**Критерий готовности:** каждая включённая заметка имеет проверяемый маршрут либо отдельно отмечена как тематическая рекомендация вне графа; циклы не приводят к повторному чтению.

**Вопросы:**

1. **C1 — критично.** Какая глубина нужна по умолчанию: 1, 2 или 3? Нужно ли задавать её в каждом запросе?
2. **C2 — критично.** Обходить исходящие ссылки, обратные ссылки или оба направления? Считать ли связи из YAML и встроенные заметки?
3. **C3.** Дополнять ли граф заметками без явных ссылок, найденными по тегам/теме? Если да, показывать их отдельным списком или добавлять как новые исходные заметки?
4. **C4.** Какие пределы удобны: максимум заметок, соседей на один узел, объём текста/токенов, время обработки?
5. **C5.** Читать статью целиком или только связанные разделы? Как обращаться с очень длинными заметками и вложениями?
6. **C6.** Включать ли в обход HUB, MOC, ежедневные заметки, архив и служебные страницы? Должна ли явная нерелевантность промежуточной заметки останавливать её ветку?

### 3.3. `obsidian-research` — исследование и доказательная база

**Кандидат для `description`:**

> Исследовать вопрос по прочитанным материалам Obsidian и разрешённым внешним источникам. Использовать для сравнения подходов, обобщения темы, выявления противоречий и пробелов. Формировать выводы с конкретными основаниями и план дальнейшего развития базы знаний.

**Вход:** вопрос, цель исследования, пакет контекста, правила внешних источников и актуальности.

**Обработка:** извлечь ключевые утверждения и определения; сопоставить терминологию; проверить, не пересказывают ли разные заметки один первоисточник; отделить подтверждённое от предположений; показать противоречия и отсутствующие данные. Внешний поиск проводить только в разрешённом режиме.

**Выход:** исследовательская записка: вопрос и охват; выводы; сравнение подходов; противоречия; пробелы; список источников; рекомендации, какие статьи создать, обновить или связать. Для существенных выводов — карта `утверждение → источник → фрагмент → степень непосредственности подтверждения`.

**Пример запроса:** «По собранным материалам сравни способы обновления графа при изменении документа».

**Критерий готовности:** центральные выводы трассируются до прочитанных материалов; ограничения охвата не скрыты; рекомендации отличаются от сведений из источников.

**Вопросы:**

1. **R1 — критично.** Исследование ограничено vault или разрешены интернет, локальные PDF, репозитории, приложенные файлы и другие источники?
2. **R2.** Какой результат важнее: краткое резюме, подробный обзор, сравнение, практическая инструкция, учебный материал?
3. **R3.** Какие критерии источников нужны: первичность, дата, открытый доступ, наличие кода, проверяемые эксперименты? Как задавать временной диапазон?
4. **R4.** Как оформлять основания: сноски, ссылки рядом с абзацами, отдельная таблица утверждений или сочетание?
5. **R5.** Как поступать с противоречиями: только показать позиции или предложить вывод с обоснованием и оговорками?
6. **R6.** Нужно ли сохранять исследовательскую записку как самостоятельную заметку? Должны ли внешние материалы получать отдельные заметки-источники?

### 3.4. `obsidian-author` — новые статьи

**Кандидат для `description`:**

> Превращать завершённое исследование в согласованный набор новых Markdown-статей для Obsidian. Использовать, когда требуется оформить полученные знания, разделить исследование на самостоятельные заметки или подготовить материалы для изучения. Учитывать существующее покрытие темы, сохранять основания выводов и связи между статьями.

**Вход:** исследовательская записка, карта существующих материалов, шаблоны, целевая аудитория и папка назначения.

**Обработка:** предложить состав статей; определить функцию каждой: понятие, метод, сравнение, инструкция, источник, обзор; избежать повторов уже существующих материалов; подготовить Markdown, YAML и ссылки; определить целевые MOC с учётом их ракурсов. Статьи должны быть понятны при самостоятельном чтении, а общий контекст переносится через ссылки.

**Обязательные правила структурирования новых статей:**

- один абзац — одна основная мысль; не объединять несколько независимых тезисов в длинный сплошной блок;
- использовать заголовки и подзаголовки как смысловые границы, пригодные для адресного чтения и RAPTOR-индексации;
- каждый крупный раздел должен отвечать на конкретный вопрос или раскрывать одну функцию;
- длинный раздел делить на подразделы до того, как потребуется слепое чанкирование по токенам;
- определения, ключевые выводы, предупреждения, примеры, ограничения, вопросы и источники при необходимости выделять Obsidian Callouts;
- не использовать callout как замену обычной структуре статьи: он выделяет важное внутри уже понятного раздела;
- сохранять естественный порядок: контекст → основная идея/механизм → детали → пример/следствия → связи и источники.

Базовые callout-типы, которые должен понимать author: `note`, `abstract`/`summary`, `info`, `tip`, `example`, `question`, `warning`, `failure`, `danger`, `quote`. Допускается согласованный пользовательский словарь типов. Каноническая форма:

```markdown
> [!summary] Ключевой вывод
> Краткая формулировка, которую полезно находить отдельно от основного текста.
```

Callout должен входить в адресуемый раздел и учитываться при RAPTOR-индексации как отдельный значимый блок, но сохранять связь с родительским heading.

**Выход:** комплект черновиков и реестр `имя → тип → назначение → целевой путь → основания → связанные заметки`. Ссылки на другие новые файлы проверять по составу пакета; до создания пакета отмечать их как запланированные. Противоречия источников не превращать в бесспорные утверждения.

**Пример запроса:** «Из исследования подготовь обзор, статью о механизме обновления и практический чек-лист».

**Критерий готовности:** у каждой статьи есть самостоятельная цель, источники и место в структуре; дублирование и ссылки на отсутствующие материалы явно обработаны.

**Вопросы:**

1. **A1 — критично.** Предпочтительны небольшие атомарные заметки, большие самостоятельные статьи или сочетание? По какому признаку делить материал?
2. **A2.** Какие типы статей и обязательные разделы нужны? Можно ли использовать существующие шаблоны?
3. **A3.** Для кого и на каком языке писать? Какой баланс пояснений, примеров, кода, формул и практических шагов?
4. **A4.** Как выбирать названия, папки и имена файлов? Нужны ли идентификаторы, префиксы и aliases?
5. **A5.** При частичном совпадении с существующей статьёй что предпочесть: дополнение, отдельный частный материал или объединение через MOC?
6. **A6 — критично.** Результат — текст/пакет файлов для просмотра или сразу новые заметки со статусом черновика в заданной папке? Нужен ли предел их числа на одно исследование?

### 3.5. `obsidian-revise` — предложения обновлений

**Кандидат для `description`:**

> Находить существующие статьи Obsidian, которые стоит дополнить или уточнить по результатам исследования, и готовить адресные предложения изменений. Использовать при появлении новых данных, повторяющегося материала или противоречий. Сохранять авторскую структуру, объяснять каждую правку и приводить её основания.

**Вход:** исследование, новые статьи, кандидаты на обновление и их актуальное содержимое.

**Обработка:** выявить смысловое пересечение; разделить исправление факта, уточнение, дополнение, новую ссылку и редакторское улучшение; найти точное место вставки; сравнить старую и новую формулировки. Сходство темы само по себе не является основанием для изменения текста.

**Выход:** пакет предложений с идентификаторами. Поля: файл, раздел, исходный фрагмент, предлагаемая редакция, причина, источники, приоритет, зависимости и версия файла, относительно которой сделана правка. Слияния и удаления отражать как отдельные рекомендации.

**Пример запроса:** «Предложи обновления существующих статей о GraphRAG на основании нового исследования».

**Критерий готовности:** каждое предложение можно понять и принять независимо; оно не затрагивает несвязанные разделы и не выдаётся за уже внесённое изменение.

**Вопросы:**

1. **U1.** В каком формате удобнее правки: таблица, «было/стало», unified diff или отдельная заметка-ревью?
2. **U2 — критично.** Что считается достаточным основанием для обновления: новый факт, исправление, практический пример, более свежий источник, кросс-ссылка?
3. **U3.** Есть ли защищённые статьи/разделы и личные формулировки, которые можно только комментировать?
4. **U4.** Как показывать устаревшие сведения: сохранять с датой, переносить в историю, предлагать замену? Как оформлять противоречащую точку зрения?
5. **U5.** Разрешено ли предлагать объединение, дробление и переименование заметок? Кто выбирает каноническую статью?
6. **U6.** Нужен ли механизм применения выбранных предложений по ID и отката? Через что удобнее проверять пакет: Obsidian, редактор или Git diff?

### 3.6. `obsidian-link` — смысловые связи и кросс-ссылки

**Кандидат для `description`:**

> Выявлять содержательные связи между Markdown-заметками Obsidian и предлагать или добавлять обоснованные перекрёстные ссылки в разрешённом объёме. Использовать для связывания новых статей с vault, поиска неявных взаимосвязей, предпосылок, альтернатив, примеров и противоречий.

**Вход:** набор заметок, тема, допустимые отношения, область поиска и лимиты ссылок.

**Обработка:** найти кандидатов по терминам, заголовкам, тегам, общим источникам и существующему графу; прочитать обе стороны; объяснить смысл связи; найти естественное место ссылки. Существующую ссылку и предлагаемую связь маркировать отдельно. Векторный поиск возможен как дополнительный механизм, если он реально подключён.

**Предлагаемые отношения:** «уточняет», «предпосылка», «пример», «применяет», «альтернатива», «противоречит», «опирается на источник». Эти типы — схема данного набора скиллов, а не автоматически распознаваемые типы рёбер Obsidian. Отдельно обрабатывать родительство MOC, принадлежность статьи MOC и последовательность этапов HUB; не выводить одно отношение из другого.

**Выход:** `статья A → статья B → отношение → обоснование → место ссылки → статус`. В новых черновиках ссылки можно сразу включить в текст; для существующих статей сформировать изменения для `obsidian-revise`. Обратная ссылка в интерфейсе не требует искусственно вставлять симметричную ссылку в текст второй статьи.

**Пример запроса:** «Свяжи статьи про идемпотентность, обновление RAG и обработку документов; объясни каждую новую связь».

**Критерий готовности:** ссылка полезна в указанном месте и ведёт к нужному файлу/разделу; одного общего тега недостаточно для подтверждения смысловой связи.

**Вопросы:**

1. **L1 — критично.** Нужны только связи внутри одной темы или также неожиданные связи между разными областями?
2. **L2.** Какие типы отношений нужны? Нужен формальный словарь или достаточно человеческого пояснения рядом со ссылкой?
3. **L3.** Где размещать ссылки: в тексте, разделе «Связанные материалы», YAML или нескольких местах?
4. **L4.** Когда нужна ссылка на статью целиком, а когда на заголовок или блок? Какой формат уже принят в vault?
5. **L5.** Сколько новых ссылок допустимо на статью? Как обращаться с полезными, но слабо подтверждёнными связями?
6. **L6.** Достаточно анализа кандидатов через Omnisearch и чтение или уже есть семантический поиск/эмбеддинги, который следует использовать? Нужны ли предложения исправления битых ссылок?

### 3.7. `obsidian-metadata` — свойства, теги и классификация

**Кандидат для `description`:**

> Формировать и проверять YAML-метаданные заметок Obsidian по принятой схеме vault. Использовать при создании статей, нормализации тегов, настройке поиска и подготовке данных для Dataview или Bases. Сохранять существующие пользовательские поля, контролировать типы и предотвращать размножение синонимичных тегов.

**Вход:** содержание статьи, существующий frontmatter, словарь тегов, тип заметки и профиль vault.

**Обработка:** выбрать тип и статус; для MOC проверить тему, ракурс и `parent_mocs`, для статей — принадлежность MOC, для HUB — метаданные в сопроводительной Markdown-заметке, если она используется; предложить темы и aliases; переиспользовать существующие теги; проверить типы свойств и корректность YAML. Для полей со списками использовать согласованный формат во всём vault. Вложенные структуры не делать основой пользовательского интерфейса свойств. [S4]

**Выход:** YAML для нового файла или предложение изменения существующего YAML; отдельный список новых тегов и конфликтов схемы. Теги, тип и статус решают разные задачи: нельзя считать, что произвольное поле `status` автоматически превращается в тег.

**Пример запроса:** «Подготовь метаданные для этих статей и проверь, не дублируют ли теги существующие».

**Критерий готовности:** YAML разбирается; обязательные поля заполнены; ссылки и типы валидны; неизвестные поля сохранены; значения позволяют выполнять согласованные запросы.

**Вопросы:**

1. **M1 — критично.** Какие поля уже приняты? Можно ли расширять схему или нужно полностью сохранить текущие имена и типы?
2. **M2.** Какой словарь типов нужен: `concept`, `guide`, `comparison`, `source`, `research`, `moc`, `hub`? Какие статусы отражают ваш процесс?
3. **M3.** Какая система тегов удобнее: свободные, контролируемые, иерархические? На русском, английском или с таблицей соответствий?
4. **M4.** Какие поля обязательны для всех заметок и какие только для источников, исследований или учебных материалов?
5. **M5.** Нужны ли постоянные ID, дата последней проверки содержания, сложность, время чтения, prerequisites и уровень уверенности? Как использовать эти поля при поиске?
6. **M6.** Какие реальные запросы нужно поддержать в Obsidian/Dataview/Bases? Например: «все черновики по RAG», «источники за год», «непроверенные статьи без MOC».

### 3.8. `obsidian-moc` — иерархические карты тем с ракурсом

**Кандидат для `description`:**

> Создавать и обновлять иерархические Map of Content в Obsidian, объединяющие статьи и дочерние MOC. Использовать для организации знаний по темам с явным ракурсом рассмотрения, построения родительских связей, аннотированных подборок и поиска подходящего места для новой статьи. Проверять согласованность иерархии и отсутствие циклов.

**Вход:** тема, ракурс, вопрос ракурса, статьи, родительский MOC при наличии, текущая иерархия и правила принадлежности.

**Подтверждено:** статьи собираются в MOC; сами MOC иерархические; у MOC есть поле, поясняющее сторону рассмотрения темы. Конкретные имена полей и правила количества родителей предлагаются в разделе 2.4.

**Обработка:** проверить существующее сочетание темы и ракурса; выбрать или предложить родителя; распределить статьи и дочерние карты; сформировать обязательный краткий `summary` MOC и компактный список `terms` основных терминов/синонимов; добавить аннотации с объяснением роли материалов в выбранном ракурсе; согласовать метаданные и видимые списки; проверить циклы, недоступные цели и противоречия структуры. Ракурс должен влиять на подбор и пояснения, а не оставаться декоративным полем. `summary` и `terms` используются как дешёвый уровень discovery до чтения тела MOC.

**Выход:** MOC-файл с обязательным именем `MOC_<Название>.md`, темой, ракурсом, обязательным summary, основными terms и областью охвата; родительские связи; разделы дочерних MOC и статей; аннотации, локальный порядок чтения и пробелы. Полный сценарий этапов работы/изучения строится в HUB. При обновлении сохраняются ручные группы и пояснения.

**Критерий готовности:** понятны положение MOC в иерархии и его ракурс; статьи соответствуют этому ракурсу; навигация согласована с `parent_mocs`; циклов нет.

**Вопросы и решения:**

1. **O1 — отвечено.** MOC объединяет статьи; MOC образуют иерархию и обязательно имеют поле ракурса. Пример существующего MOC можно предоставить для уточнения оформления.
2. **O2.** По чему группировать статьи внутри выбранного ракурса: понятия, задачи, методы, этапы или сложность?
3. **O3.** Нужны ли аннотации каждой ссылки и маркировка «обязательное / дополнительное»?
4. **O4.** Нужен ли локальный порядок чтения внутри MOC, помимо маршрута в HUB?
5. **O5.** Списки MOC должны быть статическим Markdown, динамическими подборками или сочетанием? Какие блоки остаются ручными?
6. **O6.** Когда обновлять MOC: по запросу, после исследования или при изменении включённых материалов?
7. **O7 — критично.** Допустим один родитель у MOC или несколько? Нужен ли основной родитель для навигации?
8. **O8 — критично.** Ракурс выбирается из словаря, задаётся свободным текстом или сочетанием кода и пояснения? Какие ракурсы нужны первыми?
9. **O9.** Может ли статья входить в несколько MOC? Допустима ли смена ракурса у дочернего MOC относительно родительского?
10. **O10.** Ограничивать ли глубину иерархии? Когда создавать дочерний MOC вместо раздела внутри родительского?

### 3.9. `obsidian-hub` — Canvas с маршрутами работы и изучения

**Кандидат для `description`:**

> Создавать и обновлять HUB как визуальный Canvas в Obsidian, объединяющий иерархические MOC и отдельные статьи. Использовать, когда нужен быстрый обзор этапов работы, изучения процесса или информации. Строить читаемые группы этапов, переходы, зависимости и развилки, показывать цели и результаты этапов, сохранять существующую ручную компоновку при адресных обновлениях.

**Вход:** цель HUB, режим маршрута — рабочий или учебный, аудитория, этапы/результаты, выбранные MOC и статьи, существующий Canvas при наличии.

**Подтверждено:** HUB — Canvas, объединяющий MOC и отдельные статьи для быстрого просмотра этапов работы или изучения. Нативный `.canvas` предлагается как формат реализации в Obsidian.

**Обработка:** выбрать маршрут и выделить этапы; поместить MOC/статьи в подходящие группы; подписать ракурсы MOC; добавить цели, результаты и переходы; визуально разделить альтернативы и дополнительные материалы. Использовать ссылки на исходные файлы вместо копирования их полного содержания. Иерархию MOC раскрывать только в объёме, нужном маршруту.

**Выход:** обязательная пара с общей базовой частью имени: `HUB_<Название>.md` с метаданными, summary, terms, purpose, описанием этапов/ветвей и ссылкой на Canvas; `HUB_<Название>.canvas` с группами этапов, карточками файлов и подписанными связями. Перечень добавленных/изменённых узлов и связей включается в отчёт. Прогресс не выводится из наличия материалов: для него нужны отметки пользователя.

**Проверки:** корректный JSON Canvas; уникальные ID узлов/рёбер; существование файлов и концов рёбер; разумные размеры групп и карточек; отсутствие непреднамеренных перекрытий; различимые подписи и порядок этапов. Предусмотреть визуальную проверку в Obsidian при реализации. Сохранять стабильные ID, ручные карточки, подписи и координаты; полную перекомпоновку выполнять только в согласованном режиме. Выдавать предложения изменений существующего HUB в соответствии с общей политикой записи.

**Критерий готовности:** при обзорном масштабе различимы этапы и развилки; при приближении понятны задача этапа и нужные материалы; карточки открывают оригинальные MOC/статьи.

**Вопросы и решения:**

1. **H1 — отвечено.** HUB объединяет MOC и отдельные статьи в Canvas для обзора этапов работы, изучения процесса или информации.
2. **H2.** Может ли один материал входить в несколько HUB? Как делить большой маршрут между несколькими Canvas?
3. **H3.** Кто аудитория и нужны ли отдельные маршруты для новичка и специалиста?
4. **H4.** Какие блоки этапа обязательны: цель, входные знания, материалы, действие, ожидаемый результат, критерий завершения?
5. **H5 — уточнено.** Основное представление — Canvas. Списки внутри MOC могут быть статическими или динамическими; автоматическое обновление Canvas не предполагается без определённого механизма запуска.
6. **H6.** Нужен ли прогресс изучения и откуда брать отметки? Кто инициирует обновление HUB?
7. **H7.** Как располагать этапы: слева направо, сверху вниз или дорожками для разных ролей/ракурсов?
8. **H8.** Нужны только последовательные маршруты или также параллельные этапы, альтернативы и возвраты на доработку?
9. **H9.** При обновлении сохранять ручное размещение карточек или разрешать полную автоматическую перекомпоновку? Какие правила цветов и плотности нужны?
10. **H10 — отвечено.** HUB хранится как обязательная пара `.md + .canvas`: Markdown используется для описания, поиска, Dataview/Bases и машинного чтения; Canvas — для визуального маршрута. Дополнительно остаётся вопрос о необходимости стороннего Canvas-плагина.

### 3.10. `obsidian-workflow` — полный исследовательский цикл

**Кандидат для `description`:**

> Управлять полным циклом развития тематической базы знаний Obsidian: найти исходные заметки, собрать контекст, провести исследование, подготовить новые статьи и предложения обновлений, согласовать ссылки, метаданные, MOC и HUB. Использовать для комплексных запросов с несколькими такими результатами; выбирать только необходимые этапы.

**Вход:** задача, тема, исходные материалы, ограничения, желаемые результаты, режим работы.

**Порядок работы:**

1. Загрузить профиль vault и проверить доступные инструменты.
2. Сформировать исходный набор через `obsidian-search`.
3. При необходимости отобрать материалы через `obsidian-query`, затем собрать ограниченный связанный контекст через `obsidian-context`. Динамические подборки MOC учитывать по вычисленному результату запроса с явным происхождением, отдельно от статических ссылок.
4. Подготовить выводы через `obsidian-research`.
5. Определить, что создать, что дополнить и что достаточно связать.
6. Подготовить статьи и предложения через `obsidian-author` и `obsidian-revise`.
7. Согласовать связи и метаданные через `obsidian-link` и `obsidian-metadata`.
8. При необходимости создать динамические запросы и представления через `obsidian-query-builder`. Включить статьи в подходящие MOC, проверить ракурсы и иерархию; построить или обновить HUB Canvas с этапами, MOC и отдельными статьями; проверить ссылки, метаданные и визуальную структуру.
9. Проверить пакет целиком и представить отчёт о новых материалах, предложениях, ограничениях и незавершённых действиях.

Кросс-ссылки, метаданные и навигация могут требовать небольшого повторного прохода, когда окончательно определены имена новых файлов. Скилл задаёт этот процесс; упоминание другого скилла не следует считать гарантией автоматического исполнения цепочки. Способ вызова и передача результатов должны быть определены для выбранной среды.

**Выход:** исследовательский отчёт, новые заметки, предложения изменений, иерархические MOC с ракурсами, HUB Canvas, список связей и сводка статусов. Если запись разрешена, отчёт должен различать запланированные, успешно записанные и не выполненные действия.

**Критерий готовности:** все результаты согласованы по именам, ссылкам и основаниям; повторный запуск не создаёт повторный пакет без изменений.

**Вопросы:**

1. **W1 — критично.** Какие типовые команды должен закрывать полный цикл? Приведите 2–3 примера желаемого запроса и результата.
2. **W2.** Нужны режимы «только исследование», «подготовить материалы», «создать черновики», «применить выбранные правки»?
3. **W3.** Какие решения Claude может принимать самостоятельно: число статей, разбиение темы, имена, папки, новые теги, обновление навигации?
4. **W4.** Нужен быстрый и глубокий режим? Какие пределы времени, объёма контекста и числа файлов допустимы?
5. **W5.** Должен ли повторный запуск анализировать только изменившиеся источники? Где сохранять сведения о предыдущем проходе и версиях файлов?
6. **W6.** Нужна ли автоматизация по событию или расписанию? Если да, какой внешний механизм её запускает и что считается изменением, требующим переработки?

### 3.11. `obsidian-query` — структурированный отбор материалов

**Кандидат для `description`:**

> Отбирать статьи и MOC Obsidian по метаданным, тегам, связям и вычисляемым условиям через Bases и API Dataview. Использовать для воспроизводимых тематических подборок, фильтрации по ракурсу, получения дочерних MOC, поиска пробелов в метаданных и построения состава этапов HUB. Возвращать структурированные данные с путями, условиями отбора и происхождением результата.

**Статус:** предложен по результатам проверки Obsidian CLI. Требование исследовать способы отбора получено от пользователя; выбор конкретных адаптеров и правил выполнения ещё не утверждён.

**Вход:** vault, движок (`bases`, `dataview-dql`, `dataview-api`), сохранённая выборка или условия, исходная заметка для контекста, набор выходных полей, лимит.

**Выход:** JSON со строками, однозначными путями, использованными фильтрами, временем выполнения, источником запроса/именем view, контекстом заметки, доступными версиями инструментов и признаками ошибки/усечения. Ссылки нормализовать в пути, даты — в согласованный строковый формат. Пустая выборка и ошибка исполнения — разные состояния.

**Порядок:** проверить доступность CLI/плагина и готовность индекса; выбрать сохранённый view либо получить подготовленный запрос от `obsidian-query-builder`; выполнить в нужном vault и контексте; нормализовать результат; проверить пути; передать кандидатов для чтения и анализа. Условия из пользовательского ввода передавать как данные, не вставлять без экранирования в исполняемый JavaScript или shell.

**Границы:** полнотекстовый/нечёткий поиск остаётся у Omnisearch. Этот скилл отбирает по структурированным данным; содержательные выводы требуют чтения статей. Рекурсивный обход `parent_mocs` реализует алгоритм с посещёнными узлами и пределом глубины, используя выборку как вход. Не объявлять его встроенной рекурсивной функцией Bases или DQL.

**Вопросы:**

1. **Q1.** Какой движок использовать основным: Bases для сохранённых представлений, Dataview для гибких запросов или оба?
2. **Q2 — уточнено.** Для создания запросов и представлений выделен `obsidian-query-builder`; `obsidian-query` отвечает за их выполнение и возврат данных. Правила сохранения определений уточняются в V2.

4. **Q4.** Какие выборки нужны первыми: MOC по ракурсу, дочерние MOC, статьи без MOC, материалы для обновления, состав этапа HUB?
5. **Q5.** Динамический результат MOC сохранять как снимок для исследования, оставлять живым или хранить оба варианта с датой?
6. **Q6.** Должен HUB использовать сохранённые выборки для наполнения этапов? Когда пересобирать Canvas и как сохранять ручные карточки?

### 3.12. `obsidian-query-builder` — создание запросов и представлений

**Подтверждённая задача:** отдельный скилл должен уметь писать запросы, вставлять готовые запросы в статьи и рендерить результаты для Dataview, DataviewJS и Bases. Здесь под рендерингом понимается отображение результата выборки: таблицы, списка или другого поддерживаемого представления. Конкретные формы и место предпросмотра уточняются ниже.

**Кандидат для `description`:**

> Создавать, редактировать, объяснять и проверять запросы и визуальные представления Obsidian для Dataview DQL, DataviewJS и Bases; вставлять новые и готовые запросы в статьи и MOC, обновлять существующие блоки без дублирования. Использовать, когда пользователь описывает нужную выборку обычным языком, просит добавить динамический список или таблицу в MOC, подготовить подборку для этапа HUB, исправить запрос или изменить его отображение. Учитывать схему метаданных vault, иерархию MOC и ракурсы; готовить исполняемый запрос, отображать результат доступным способом и явно сообщать уровень проверки.

**Разделение ответственности:** `obsidian-query-builder` создаёт и изменяет определение выборки и её представление; `obsidian-query` выполняет запрос и возвращает нормализованные данные; `obsidian-moc` определяет место подборки в карте; `obsidian-hub` отвечает за Canvas, этапы и размещение карточек. Динамическая таблица сама по себе не перестраивает структуру Canvas.

**Вход:** задача пользователя либо готовый запрос/путь к существующему `.base` или JS view; выбранный инструмент либо режим `auto`; схема свойств и реальные примеры заметок; область поиска; фильтры; выводимые поля; сортировка, группировка и лимит; контекст текущей заметки; целевая статья/MOC и раздел, якорь либо ID блока; режим вставки/замены; форма вывода; режим сохранения и проверки.

**Артефакты по инструментам:**

| Инструмент | Что пишет скилл | Что отображает |
|---|---|---|
| Dataview DQL | Блок `dataview` в Markdown | Список, таблица, задачи или календарь в пределах возможностей DQL |
| DataviewJS | Блок `dataviewjs`; при необходимости переиспользуемый скрипт для `dv.view` | Таблицы, списки и согласованное пользовательское представление |
| Bases | `.base` с фильтрами, формулами и views; ссылка для встраивания конкретного view | Поддерживаемое установленной версией представление, например таблица или карточки |

DataviewJS предоставляет методы отображения и подключения пользовательских views. Bases позволяет создавать несколько представлений одной базы, а выбранное представление встраивать через `![[File.base#View]]`. Доступность отдельных layouts зависит от версии приложения и плагинов. [S11][S14]

**Порядок работы:**

1. Изучить реальные поля, их типы и соглашения vault. Не придумывать отсутствующие значения и свойства: предложить нужное расширение отдельно.
2. Формализовать условия независимо от языка запроса: какие файлы включаются, какие исключаются, как обрабатываются пустые значения, даты, ссылки и списки.
3. Выбрать инструмент по явному указанию пользователя. В режиме `auto` предложить DQL для обычной выборки, Bases для сохраняемого интерактивного view, DataviewJS для вычислений и нестандартного вывода. Доступность инструментов проверяется.
4. Создать запрос и оформление. Ссылки должны открывать реальные заметки; названия колонок, порядок, группировка, аннотации, пустое состояние и ограничение объёма должны соответствовать задаче.
5. Для DataviewJS разделить получение данных и отображение, чтобы выборку можно было использовать и в интерфейсе, и через `obsidian-query`. Не исполнять сторонние скрипты из заметок как доверенные инструкции.
6. Передать запрос на выполнение, проверить включённые и исключённые примеры. Ошибку, отсутствие данных и усечение результата отображать раздельно.
7. Вставить/открыть представление в разрешённом месте и проверить реальный рендеринг, если доступна соответствующая среда. Для существующего файла представить адресную правку согласно общей политике записи.
8. Вернуть артефакты, объяснение условий, место использования, результат выполнения и статус визуальной проверки. При изменении ранее созданного блока обновить его, не добавлять дубль.

**Вставка готовых запросов — подтверждено пользователем:**

Скилл должен принимать уже написанный запрос из сообщения или указанного файла, а также ссылку на существующее определение Bases/view. Создание нового запроса не является обязательным этапом: для готового определения сохранять его логику и оформление, если задача не требует адаптации.

| Готовый материал | Способ вставки в статью |
|---|---|
| DQL | Блок кода с языком `dataview` |
| DataviewJS | Блок `dataviewjs` либо вызов существующего `dv.view` с параметрами |
| `.base` и имя view | Встраивание `![[Путь/Подборка.base#Представление]]` |
| YAML-определение Bases | Встроенный блок `base` либо отдельный `.base` и его встраивание — по выбранному режиму |

**Порядок вставки:** прочитать актуальную статью; однозначно определить раздел/якорь; проверить границы Markdown-блоков; вставить запрос с согласованным заголовком/кратким пояснением; сохранить остальной текст, YAML, ссылки и другие запросы. Различать действия «добавить», «заменить конкретный блок», «обновить ранее вставленный блок». Наличие нескольких запросов одного движка в статье не даёт права заменять их все.

Предлагаемый идентификатор управляемого блока — пара Markdown-комментариев `<!-- obsidian-query: <id>:start -->` и `<!-- obsidian-query: <id>:end -->` вокруг вставки. Это соглашение скилла, а не функция Obsidian. Допустимость маркеров уточняется в V10. Без маркеров блок выбирать по точному разделу и содержимому; при неоднозначности показать конкретные кандидаты.

**Контекст и проверка:** перед вставкой проверить, не меняет ли новая статья значения `this`, `dv.current()` и разрешение относительных ссылок. При необходимости адаптации объяснить различие; не менять смысл готового запроса молча. После вставки перечитать изменённый участок, выполнить запрос при доступности инструментов и проверить отображение в целевой статье при доступности Obsidian. В результате указать файл, раздел, движок, действие, ID блока и уровень проверки. Нельзя назвать проверку выполненной, если доступен только исходный код.

**Политика применения:** явная команда «вставь этот запрос в эту статью» разрешает адресную вставку в названную статью без дополнительного согласования той же операции. Это отличается от исследовательских предложений изменить содержание старых статей. Текущее уточнение задаёт возможность будущего скилла; реальные статьи пользователя сейчас не изменялись.

**Уровни проверки:**

- `generated`: код подготовлен, исполнение не проверено;
- `executed`: запрос выполнен в целевом vault и возвращает данные/пустой результат без ошибки;
- `rendered`: представление открыто и визуально проверено в Obsidian с целевым контекстом.

JSON от CLI подтверждает получение данных, но не визуальную корректность таблицы или карточек. Статический Markdown-предпросмотр полезен как дополнительный результат, однако не заменяет проверку живого представления. Если к Obsidian нет доступа, вернуть подготовленные файлы с честным статусом `generated` и точным способом их проверки; не объявлять визуальную проверку выполненной.

**Условия корректности:**

- Проверять источник `this`/`dv.current()` и относительные пути в месте встраивания.
- Различать полный обход дерева MOC, прямых детей и обычные ссылки. Рекурсию реализовывать только там, где предусмотрена алгоритмическая поддержка, с лимитами и защитой от циклов.
- Для подборки статей по ракурсу сначала определять подходящие MOC, затем принадлежность статей. Не требовать поле `perspective` у статей автоматически.
- Не обещать точную конвертацию произвольного DataviewJS в DQL/Bases. При различиях возможностей описать изменение поведения и предложить подходящий инструмент.
- Не менять метаданные заметок ради успешного выполнения запроса без отдельного основания.
- Ограничивать количество отображаемых строк/карточек, избегать многократного полного сканирования vault при рендеринге.
- Сохранять существующие запросы, ручные секции и элементы оформления вне запрошенной правки.

**Примеры запросов пользователя:**

- «Сделай Dataview-таблицу дочерних MOC, покажи их ракурс и описание».
- «Напиши DataviewJS, который соберёт статьи всех дочерних MOC до глубины 2 и сгруппирует по статусу».
- «Создай Bases с представлениями “Все материалы”, “Нужно обновить” и “Без MOC”, вставь нужный view в карту».
- «Покажи результат запроса в Obsidian и поправь ширину/состав таблицы».
- «Вставь этот DataviewJS в статью “Индексация RAG”, в раздел “Связанные материалы”».
- «Встрой представление “Operations” существующей базы в этот MOC».
- «Обнови ранее вставленный запрос в статье, сохрани остальной текст».
- «Перенеси этот запрос в другой инструмент, сохрани условия отбора и объясни ограничения».

### Каталог переиспользуемых запросов

Dataview/Bases, которые уже применялись для полезного поиска, должны по возможности сохраняться внутри vault как переиспользуемые определения, а не генерироваться заново каждый раз.

Предлагаемая структура:

```text
System/Queries/
├── README.md
├── Dataview/
│   ├── Articles without MOC.md
│   └── Recent RAG sources.md
├── Views/
│   └── Knowledge Maintenance.base
└── Scripts/
    └── moc-tree.js
```

`System/Queries/README.md` является каталогом. Для каждого определения хранить:

- человекочитаемое имя и ID;
- назначение и пример вопроса, для которого оно полезно;
- движок: Dataview DQL / DataviewJS data adapter / Bases;
- входные параметры и зависимые YAML-поля;
- scope и ограничения;
- когда использовать и когда не использовать;
- ссылку на файл запроса или `.base#View`;
- примеры MOC/HUB/статей, где запрос встроен;
- статус проверки (`generated`, `executed`, `rendered`);
- дату последней проверки и при необходимости версию схемы.

Если retrieval-оркестратор находит подходящий сохранённый запрос, он должен переиспользовать его до генерации нового. Новое определение, доказавшее полезность в повторяемом сценарии, предлагается добавить в каталог.

**Выход:** запрос/определение view; код рендеринга или настройки представления; целевой путь и место вставки; объяснение условий; пример или реальный результат с маркировкой; статус проверки; выявленные ограничения. Переиспользуемым определениям назначать стабильный ID; контекст, параметры и формат вывода хранить вместе с определением в согласованном реестре или файле.

**Критерий готовности:** запрос реализует согласованные условия, ссылается на реальные поля, представление соответствует задаче, уровень проверки обозначен; повторное применение не создаёт дубли. Для полного режима нужны и корректная выборка, и проверенный рендеринг в Obsidian.

### 3.13. `obsidian-semantic-search` — RAPTOR semantic retrieval

**Назначение:** искать релевантные материалы по смыслу на нескольких уровнях иерархии, не читая исходные статьи целиком.

**Вход:** query, scope, mode (`narrow|deep`), уровни поиска (`article|section|subsection|chunk|auto`), metadata filters, top-k, token budget.

**Обработка:** сначала искать по summary верхних уровней; при высокой релевантности раскрывать дочерние узлы. Учитывать heading path и границы Markdown. Возвращать score и provenance, но не использовать generated summary как окончательное доказательство факта.

**Выход:** `RaptorMatch[]`: path, heading path, node ID/level, score, summary, line/paragraph range, parent/children, estimated read cost.

**Связь:** точное чтение исходного текста выполняется через `obsidian-fragment-reader`.

### 3.14. `obsidian-retrieve` — оркестратор hybrid retrieval

**Назначение:** получить минимально достаточный набор кандидатов под задачу, объединяя Omnisearch, terms, RAPTOR, Dataview/Bases и граф.

**Режим `narrow`:** высокая точность, малый top-k, progressive expansion и ранняя остановка после получения достаточного evidence.

**Режим `deep`:** широкий recall, несколько поисковых формулировок, больше MOC/graph expansion, итеративный поиск пробелов и противоречий.

**Обработка:** построить search plan; при возможности выполнить Dataview/Bases pre-filter; запустить нужные retrievers; объединить и дедуплицировать результаты; учесть MOC/graph proximity; оценить стоимость чтения; сформировать `CandidateSet`.

**Выход:** кандидаты, причины отбора, использованные механизмы, итоговое ранжирование, budget usage, рекомендации что раскрывать дальше.

### 3.15. `obsidian-fragment-reader` — адресное чтение фрагментов

**Назначение:** читать только конкретный абзац, диапазон абзацев, раздел или подраздел статьи; расширять область только при необходимости.

**Вход:** path + один из адресов: heading, heading path, paragraph/block ID, line range, RAPTOR node ID. Дополнительно: `include_children`, `child_depth`, `max_tokens`.

**Правила:**

1. Если указан RAPTOR node, разрешить его обратно до исходного Markdown.
2. Для абзаца вернуть его heading context; для подраздела — заголовок и тело до следующего заголовка того же/более высокого уровня.
3. `include_children=true` добавляет только дочерние подразделы до заданной глубины.
4. Не добавлять соседние разделы «для контекста» без причины.
5. Возвращать точный path, heading path, границы, content hash и объём прочитанного текста.
6. Callouts внутри выбранного диапазона сохранять как отдельные семантические блоки.
7. Если фрагмент ссылается на определение вне диапазона и без него смысл неоднозначен, вернуть `needs_context` с адресом, а не автоматически читать всю статью.

**Выход:** `Fragment[]` + сведения о частичном чтении.

### 3.16. `obsidian-evidence` — точные выдержки и основания

**Назначение:** превратить CandidateSet в минимальный набор исходных фрагментов, достаточный для конкретных утверждений.

**Обработка:** запросить через fragment-reader исходные passages; объединить дубли; отделить прямое подтверждение от интерпретации; при необходимости запросить один дополнительный соседний/дочерний фрагмент.

**Выход:** `EvidenceItem`: claim/question facet, file, heading path, fragment, paraphrase/short quote, directness, retrieval methods, confidence, read cost.

### 3.17. `obsidian-qa` — narrow QA и insight mining

**Назначение:** отвечать на точные вопросы и извлекать полезные инсайты из vault при минимальном расходе контекста.

**Pipeline:** intent → `obsidian-retrieve(mode=narrow)` → summaries → адресное раскрытие RAPTOR-ветвей → `obsidian-evidence` → answer.

Для insight mining разрешён расширенный вариант narrow-поиска: сопоставление нескольких evidence clusters, поиск повторяющихся паттернов, противоречий и неожиданных связей. Если для вывода требуется широкий обзор темы, skill должен эскалировать задачу в `obsidian-research(mode=deep)`, а не незаметно читать десятки статей.

**Критерий готовности:** ответ трассируется до минимального набора исходных фрагментов; в отчёте можно показать, какие уровни RAPTOR были раскрыты и сколько текста реально прочитано.


## 4. Предлагаемая схема метаданных

### 4.1. Статьи

Обязательное ядро для обсуждения: `type`, `status`, `tags`, `created`, `updated`. `aliases` и `summary` полезны, но могут быть опциональными. Перед внедрением схему нужно сверить с текущими свойствами vault; значения ниже — иллюстрация, а не миграция существующих файлов.

Пример для новой статьи; все названия заметок условные:

```yaml
---
type: concept
status: draft
tags:
  - rag/graph
  - rag/updates
aliases:
  - Incremental GraphRAG
summary: Подходы к обновлению графового индекса при изменении документов.
created: 2026-09-28
updated: 2026-09-28
topics:
  - "[[Topics/GraphRAG]]"
sources:
  - "[[Sources/Исходная публикация об обновлении графа]]"
moc:
  - "[[Maps/MOC_Обновление GraphRAG]]"
hub:
  - "[[Hubs/HUB_RAG и системы знаний.canvas]]"
---
```

| Поле | Тип | Назначение |
|---|---|---|
| `type` | Текст | Роль заметки |
| `status` | Текст | Стадия работы с заметкой |
| `tags` | Список тегов | Фильтрация и классификация |
| `aliases` | Список | Альтернативные имена |
| `summary` | Текст | Краткое содержание |
| `created`, `updated` | Дата | Создание и содержательное изменение |
| `topics` | Список ссылок | Сущности или тематические заметки |
| `sources` | Список ссылок/URL | Основания статьи в целом |
| `moc`, `hub` | Списки ссылок | Навигационная принадлежность |

В YAML внутренние ссылки следует заключать в кавычки. `tags` — специальное свойство Obsidian; произвольные свойства вроде `topics` и `status` не становятся тегами автоматически. По ним используют поиск по свойствам или запросы выбранного плагина. [S4]

Дополнительные поля вводятся под конкретную потребность: для источника — `source_url`, `authors`, `published`, `accessed`; для учебной статьи — `difficulty`, `prerequisites`; для регулярной проверки — `reviewed`. Не добавлять их ко всем заметкам без пользы для поиска и работы.

`created` сохраняется при редактировании. `updated` меняется при реальном содержательном обновлении, а не при каждом запуске скилла. Внешняя дата публикации и дата создания локальной заметки — разные данные.

Список `sources` помогает навигации, но точные утверждения всё равно должны иметь основания в теле заметки. Формат внутренних ссылок может включать статью, её заголовок или блок: `[[Путь/Статья]]`, `[[Путь/Статья#Раздел]]`, `[[Путь/Статья#^block-id]]`. Проверять существование адресата и не добавлять block-id в чужую статью без предусмотренного изменения. [S5]

### 4.2. MOC: тема, ракурс и родительство

Имена полей — предложение. Все ссылки в примере условные:

```yaml
---
type: moc
status: draft
topics:
  - "[[Topics/Индексация RAG]]"
perspective: operations
perspective_question: Как обновлять индекс без потери актуальности и доступности?
summary: Карта практик обновления RAG-индекса в эксплуатации: инкрементальные изменения, переиндексация, консистентность и контроль актуальности.
terms:
  - incremental indexing
  - reindex
  - freshness
  - consistency
  - GraphRAG
parent_mocs:
  - "[[Maps/MOC_RAG - Эксплуатация]]"
tags:
  - rag/indexing
  - perspective/operations
created: 2026-09-28
updated: 2026-09-28
---
```

В начале тела MOC обязательны секции `## Summary` и `## Основные термины`. Summary — 1–3 компактных абзаца о том, что покрывает MOC и чем этот ракурс отличается от соседних. Основные термины — короткий список ключевых терминов, синонимов, английских/русских вариантов и устойчивых названий технологий, используемый быстрым lexical/term retrieval. Далее показать родителя, дочерние MOC и статьи с аннотациями. `perspective` отвечает за ракурс и фильтрацию, `perspective_question` — за его конкретный смысл. Тег ракурса опционален; при его использовании проверять соответствие основному полю.

`parent_mocs` — источник родительства; видимые списки дочерних карт выводятся/обновляются по нему. Поле `moc` у статьи хранит прямую принадлежность; аннотированные списки статей в MOC должны с ней согласовываться. При расхождении существующих данных показать конфликт и предложить исправление, а не автоматически удалять вручную выбранные статьи.

### 4.3. HUB: обязательная пара Markdown-описание + Canvas

Для схемы с сопроводительной Markdown-заметкой предлагаются:

```yaml
---
type: hub
status: draft
purpose: Пройти этапы разработки и проверки RAG для документов.
summary: Маршрут от постановки задачи и подготовки данных до retrieval, evaluation и эксплуатации.
terms:
  - RAG
  - retrieval
  - indexing
  - evaluation
  - operations
route_type: workflow
canvas: "[[Hubs/HUB_Разработка RAG.canvas]]"
tags:
  - rag
  - navigation/hub
created: 2026-09-28
updated: 2026-09-28
---
```

`route_type` может быть `workflow` или `learning` как согласованный словарь. Несколько маршрутов могут использовать одни и те же MOC/статьи. Позиция статьи в конкретном HUB хранится на стороне маршрута/Canvas и не задаётся глобальным `stage` в статье: в другом HUB эта статья может выполнять другую роль.

Markdown-файл HUB является обязательным и должен содержать минимум:

```markdown
# HUB — <Название>

## Summary
Краткое описание назначения и границ маршрута.

## Основные термины
- ...

## Этапы
### 1. ...
Цель, входы, ключевые MOC/статьи, ожидаемый результат.

## Ветвления и альтернативы
...

## Связанный Canvas
![[HUB_<Название>.canvas]]
```

Canvas остаётся самостоятельным JSON-файлом. Для поиска маршрутов и чтения контекста в первую очередь используется Markdown-описание; чтение `.canvas` необходимо для геометрии, визуальных групп и рёбер. Отсутствие такой возможности нельзя скрывать под обычным поиском Markdown.


### 4.4. Реестр Dataview/Bases и поисковых представлений

Рекомендуемая папка: `System/Queries/`. Это часть базы знаний, а не внутреннее состояние Claude.

Минимальные типы артефактов:

- `.base` — сохраняемые интерактивные выборки;
- `.md` с DQL — документированный Dataview-запрос и пример результата;
- `.js`/view — только для согласованных DataviewJS data adapters;
- `README.md` — индекс всех сохранённых запросов.

Пример записи в каталоге:

```markdown
### Articles without MOC
- **Engine:** Dataview DQL
- **Use when:** нужно найти статьи, ещё не встроенные в структуру MOC
- **Do not use when:** нужно искать семантическое содержание статей
- **Requires:** `type`, `moc`
- **Definition:** [[System/Queries/Dataview/Articles without MOC]]
- **Used by:** [[MOC_Knowledge maintenance]]
- **Status:** executed
```

Ссылки на сохранённые запросы могут храниться в MOC/HUB, если они являются частью пользовательского представления. Retrieval-слой использует реестр как библиотеку воспроизводимых структурных pre-filter'ов.


## 5. Общие форматы передачи результатов

Это логические контракты; реализация может использовать Markdown, JSON или комбинацию. Не обязательно создавать отдельный файл для каждого промежуточного результата.

| Объект | Минимальные данные |
|---|---|
| Результат поиска | Запрос, vault, путь, название, вид совпадения, retrieval method, ссылка, ранжирование при доступности |
| RAPTOR match | Путь, heading path, node level/ID, summary, score, диапазон исходного текста, parent/children, estimated read cost |
| Fragment | Путь, heading path, точный диапазон, текст, child depth, content hash, фактически прочитанные токены |
| Evidence item | Вопрос/утверждение, точный fragment, непосредственность подтверждения, confidence, retrieval provenance |
| Элемент контекста | Путь, глубина, маршрут/предшественник, направление и тип связи, выбранные разделы, статус чтения |
| Основание вывода | Утверждение, источник, точное место, фрагмент или парафраз, первичный/вторичный доступ |
| Новая статья | Целевой путь, роль, текст, метаданные, основания, запланированные и существующие связи |
| Предложение правки | ID, файл и раздел, старая/новая версия фрагмента, причина, источники, зависимости, версия прочитанного файла |
| Предложение связи | Начальный и целевой пути, тип отношения, обоснование, место вставки, статус |
| MOC | Тема, ракурс, summary, terms, вопрос ракурса, родители, дочерние MOC, статьи и аннотации |
| HUB | Markdown-описание, summary, terms, Canvas, этапы, цели/результаты, карточки файлов, переходы и их типы |
| Итог запуска | Параметры, охват, ограничения, созданные материалы, предложения, ошибки, пропущенные действия |

Допустимые статусы чтения: «найдено», «прочитано частично», «прочитано», «недоступно». Для частичного чтения указывать использованные разделы. Необработанные документы нельзя включать в число изученных.

Для контекста полезны три независимых ограничения: глубина, число уникальных заметок, объём читаемого текста. Например, глубина 2 не гарантирует малый объём, если первая заметка ссылается на большой HUB.

## 7. Как оценивать готовый набор

| Сценарий | Ожидаемый результат |
|---|---|
| Две заметки с одинаковым именем в разных папках | Однозначные пути или явно обозначенный выбор; ссылки не подменяются |
| У запроса есть сокращение и английский вариант | Расширение запроса соответствует настройкам и отражено в отчёте |
| Цикл A → B → A | Каждая заметка обрабатывается один раз, повторная связь сохраняется |
| Один HUB с сотнями ссылок | Соблюдаются лимиты и тематический отбор, показано усечение контекста |
| Статья есть только в выдаче, но не читается | Она не используется как изученное основание |
| Две заметки повторяют одну публикацию | Это один первоисточник, а не два независимых подтверждения |
| Источники противоречат друг другу | Противоречие показано, синтез не скрывает различия |
| Новая тема уже частично описана | Предлагается осмысленное дополнение или отдельный частный материал |
| YAML содержит неизвестные поля | Они сохраняются; типы общих свойств не меняются молча |
| Предлагается смысловая связь без явной ссылки | Она маркируется как предложение с обоснованием |
| Файл изменён пользователем после анализа | Правка пересобирается относительно актуального текста |
| Повторный запуск с теми же данными | Нет дублей статей, ссылок, тегов и одинаковых правок |
| Цикл в родительстве MOC | Цикл выявлен; правка не выдаётся за корректную иерархию |
| Одна тема в разных ракурсах | Различаются критерии отбора и аннотации, ракурс виден в каждом MOC |
| Статья нужна двум MOC и HUB | Используются ссылки на один исходный файл; текст не копируется |
| HUB содержит этапы и альтернативы | Переходы подписаны, карта читается в обзорном масштабе |
| Обновление Canvas с ручной компоновкой | Сохраняются ID, пользовательские узлы и координаты вне согласованных изменений |
| Часть новых файлов не создана | Отчёт не объявляет весь пакет готовым; зависимые ссылки отмечены |
| Narrow-вопрос покрывается одним подразделом | Читается подраздел/несколько абзацев, а не статья целиком |
| RAPTOR нашёл релевантный summary | Перед доказательным выводом reader открывает исходный fragment |
| Deep research требует расширения | Retrieval выполняется итеративно и раскрывает только перспективные ветви |
| MOC используется для быстрого discovery | Summary и terms позволяют отобрать карту без чтения полного тела |
| Создаётся новый MOC | Имя файла соответствует `MOC_<Название>.md` |
| Создаётся или обновляется HUB | Markdown и Canvas образуют пару `HUB_<Название>.md` + `HUB_<Название>.canvas` |
| Найден старый MOC/HUB без префикса | Skill не переименовывает его молча; показывает конфликт соглашения и предлагает миграцию |
| HUB найден по теме | Сначала читается HUB.md; Canvas открывается только для маршрута/геометрии |
| Полезный Dataview/Bases запрос повторяется | Он переиспользуется из `System/Queries`, а не генерируется заново |
| Статья содержит длинный неструктурированный блок | Author/revise предлагает деление на смысловые абзацы и подзаголовки |
| Callout попал в релевантный RAPTOR-узел | Reader сохраняет тип callout и связь с родительским heading |

## 8.1. Целевая схема исполнения

### Narrow QA

```text
question
  → obsidian-retrieve(mode=narrow)
      → Dataview/Bases pre-filter when useful
      → Omnisearch / term / RAPTOR
      → fusion + dedup + ranking
  → obsidian-fragment-reader
  → obsidian-evidence
  → obsidian-qa
```

Ожидаемое поведение: ранняя остановка после получения достаточного evidence. Полный `obsidian-research` не запускается.

### Deep research и запись новых знаний

```text
research question
  → obsidian-retrieve(mode=deep)
  → summaries / MOC / HUB map
  → targeted fragment expansion
  → obsidian-research
  → поиск пробелов и второй retrieval pass при необходимости
  → placement decision:
      existing article → obsidian-revise
      new concept/material → obsidian-author
  → obsidian-link + obsidian-metadata
  → obsidian-moc
  → obsidian-hub only when route/navigation changes
```

### Placement decision

Перед созданием новой статьи обязательно проверить:

1. существует ли статья с тем же смысловым ядром;
2. можно ли встроить новый материал как отдельный раздел/подраздел;
3. нужен ли самостоятельный материал из-за другой цели, уровня детализации или ракурса;
4. к каким MOC он относится;
5. изменяет ли он структуру HUB или только содержание существующего узла.

### Требования к реализации RAPTOR-индекса

Индекс должен обновляться инкрементально. Content hash позволяет переиндексировать только изменившиеся абзацы/разделы и пересчитать зависимые summaries вверх по дереву. Удаление/переименование heading должно инвалидировать адреса дочерних узлов. Векторное хранилище не является источником истины: исходный Markdown остаётся каноническим текстом.

## 10. Проверка Obsidian CLI: Bases, Dataview и DataviewJS

Проверено по документации 2026-09-28. На компьютере пользователя команды не запускались; версии, плагины и результат конкретного подключения ещё предстоит проверить.

### 10.1. Доступные способы

| Источник | Способ доступа | Применение в проекте |
|---|---|---|
| Bases | Нативная команда `base:query` с `.base` и именем view | Сохранённые пользовательские выборки |
| Dataview DQL | `eval` и API загруженного Dataview | Запросы по полям, задачам и связям |
| Dataview JavaScript API | `eval` и `app.plugins.plugins.dataview.api` | Сложные вычисляемые отборы |
| Готовый DataviewJS-блок | Отдельная адаптация логики или контекст рендеринга | Переиспользование существующих дашбордов, если нужно |

CLI документирует `base:query` с форматами JSON, CSV, TSV, Markdown и paths, а также `eval` для выполнения JavaScript. Используется работающее приложение; документация установки указывает installer 1.12.7+ и включение CLI в настройках. [S8]

Bases хранит определения в `.base` YAML: фильтры базы и view, формулы и настройки представлений. Доступны свойства файлов и frontmatter, условия AND/OR/NOT, работа с тегами и ссылками. Inline-поля Dataview не считать свойствами Bases автоматически. Контекст `this` зависит от места отображения базы; соответствие встроенного view и CLI-запроса нужно проверять. [S9]

Dataview предоставляет API через `app.plugins.plugins.dataview.api`. Его индекс содержит свойства и сведения о страницах; сам текст произвольных абзацев не является индексируемым полем. Полное чтение заметки остаётся отдельной операцией. [S10][S13]

### 10.2. Примеры для проектирования адаптеров

Названия vault, файлов и view ниже условные. Это иллюстрации, не отчёт об успешном выполнении.

Сохранённое представление Bases:

```bash
obsidian vault="Research" base:query path="Views/MOC.base" view="Operations" format=json
```

В определении этого view можно выбрать `type == "moc"` и `perspective == "operations"`. Поле ракурса относится к MOC; не следует ожидать такого же поля у каждой включённой статьи. Статьи по ракурсу получают через принадлежность подходящим MOC.

Синхронная выборка через Dataview API, пригодная для передачи в `eval`:

```javascript
(() => {
  const dv = app.plugins.plugins.dataview?.api;
  if (!dv) throw new Error("Dataview API unavailable");
  const rows = dv.pages()
    .where(p => p.type === "moc" && p.perspective === "operations")
    .map(p => ({ path: p.file.path, perspective: p.perspective }))
    .array();
  return JSON.stringify(rows);
})()
```

Исполнитель должен возвращать результат, обрабатывать ошибку и сохранять согласованный контракт JSON. Проверка наличия API не заменяет проверку готовности индекса после запуска приложения.

DQL для прямых дочерних MOC:

```dataview
TABLE WITHOUT ID file.link AS MOC, perspective AS Perspective
WHERE type = "moc"
  AND contains(parent_mocs, [[Maps/MOC_RAG - Эксплуатация]])
SORT file.name ASC
```

Его можно передать в `api.query(queryText, originFile)`; метод асинхронный и возвращает результат/ошибку. `queryMarkdown` возвращает Markdown для поддерживаемых типов вывода. В адаптере CLI нужно проверить ожидание Promise и формат вывода на установленной версии, а не выдавать объект Promise за данные. [S11][S12]

### 10.3. Почему DataviewJS требует отдельного контракта

Отбор `pages(...).where(...).map(...)` можно выполнить через API и преобразовать в обычные данные. Но `dv.table`, `dv.el`, `dv.view`, `dv.current` и пользовательские обработчики могут зависеть от контейнера, текущей заметки и жизненного цикла представления. API `executeJs` принимает контейнер и контекст рендеринга; он не является универсальным преобразователем произвольного блока в JSON. [S11][S12]

Предлагается отделять функцию получения данных от функции отображения: одна и та же выборка используется скиллом и визуальным блоком MOC. Существующие блоки сначала классифицировать; не исполнять извлечённый из заметки произвольный JS автоматически. Для первой версии достаточно ограниченного адаптера запросов, не требующего воспроизведения UI.

### 10.4. Связь с моделью знаний

- Omnisearch находит кандидатов по названиям и тексту.
- Bases задаёт сохраняемые, просматриваемые пользователем выборки.
- Dataview API обеспечивает дополнительные вычисления и объединение результатов.
- `obsidian-context` обходит выбранную иерархию/связи с ограничениями.
- `obsidian-moc` и `obsidian-hub` используют отобранные материалы для организации знаний и маршрутов.

При строгом фильтре по ракурсу сначала отобрать MOC, затем их статьи. Найденная Omnisearch статья может войти в выборку через MOC даже без собственного `perspective`. Если статья подходит теме, но пока не имеет нужной принадлежности, показать её отдельным кандидатом на включение.

Динамические ссылки, показанные запросом MOC, не следует считать гарантированно записанными wikilinks исходного файла. Сохранять происхождение: MOC, определение запроса/view, контекст, время выполнения, полученные пути. Для исследования фиксировать снимок выборки; изменение запроса или данных может изменить её состав.

Примеры целевых выборок: MOC в ракурсе эксплуатации; прямые дети выбранного MOC; все потомки до заданной глубины; статьи этих MOC с нужным статусом; статьи без назначенного MOC; материалы, изменившиеся после последнего исследования; материалы для конкретного этапа HUB. Рекурсивные и сравнительные задачи требуют логики адаптера и/или сохранённых результатов предыдущего прохода.

| Narrow | Omnisearch top-5, RAPTOR top-8, merged 8–12, graph depth 1, fragment expansion 3–6, target 4–6k tokens, 1 pass. |
| Deep | Omnisearch top-20, RAPTOR top-25, merged 30–40, graph depth 2, fragment expansion 15–25, target 20–30k tokens/pass, до 2 passes. |
| Early stop | Narrow: все части вопроса имеют прямое основание без существенного обнаруженного конфликта; deep: новый pass не выявляет классов evidence/конфликтов/подтем, меняющих synthesis. Не вводить универсальный vector score threshold. |
| Callouts | Стандартные `[!summary]`, `[!info]`, `[!tip]`, `[!example]`, `[!question]`, `[!warning]`, `[!failure]`, `[!danger]`, `[!quote]`; без зависимости от custom CSS. |

Reusable query сохраняется, если встроен в постоянный MOC/HUB, использован успешно дважды или явно запрошен. `System/Queries/` содержит `README.md`, `Dataview/`, `Bases/`, `Scripts/` и временный `_sandbox.md`. Одноразовый эксперимент каталог не засоряет.


## 12. Развитие спецификации и трассировка

[Структура и коды](structure.md) определяют постоянные идентификаторы `REQ-<DOMAIN>-NNNN`, заморозку исходных ID через ссылки `LEG-*`, статусы, критерии `AC-REQ-...` и процедуру нового требования. [Реестр требований](requirements-registry.md) выдаёт следующий номер и связывает нормы с проверками. [User stories](user-stories.md) показывают, какую цель пользователя реализуют skills. [Индекс документации](../index.md) ведёт к алгоритмам, планированию, проверкам и ADR.

Новая норма не получает очередной код старой серии (`S7` и т. п.) и не переписывает исходный вопрос. Сначала определить story и существующие основания, затем зарегистрировать ID/приёмку, обновить нужный раздел спецификации, реализацию, алгоритмы/карты и при существенном выборе — ADR. Явное новое требование пользователя имеет приоритет; принятую ранее норму заменять с `supersedes`, сохраняя старый ID доступным.
