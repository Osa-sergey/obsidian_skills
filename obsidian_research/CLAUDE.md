# Obsidian Knowledge Vault Skills — инструкция для разработки

## Где искать требования

Начинай с [карты документации](docs/index.md) и [индекса спецификации](docs/spec/index.md). Открой паспорт нужного skill, связанные общие разделы и дефолты; не загружай все 19 файлов. Индексы помогают найти нормативный текст, но не заменяют его. При расхождении исправь навигатор. Не считай описанную функцию уже реализованной: проверь код и окружение.

- [Паспорта skills](docs/spec/skills/index.md) — отдельный файл для каждого skill; [карта](docs/skills-map.md) — зависимости.
- [User stories](docs/spec/user-stories.md) — пользовательская цель функции.
- [Коды требований](docs/spec/structure.md) и [реестр](docs/spec/requirements-registry.md) — как добавлять требования без коллизий.
- [Алгоритмы](docs/algorithms.md) — retrieval, адресное чтение, запись, MOC/HUB, запросы.
- [Пробелы и внешний поиск](docs/spec/skills/19-obsidian-gap-search.md) — проверь покрытие HUB/MOC по фрагментам, затем составь запросы; найденные источники отдельно проверяет research.
- [Дефолты](docs/defaults-map.md) — принятая политика и границы настройки.
- [Планирование](docs/planning.md) — формат плана изменений и проверки.
- [Проверка](docs/verification.md) — критерии для затронутых контрактов.
- [Запись в Git](docs/git-change-record.md) — как зафиксировать результат изменения.
- [Архитектурные решения](docs/adr/index.md) — принятые решения и их причины.

## Инварианты

1. Исходный Markdown — источник истины; поисковый индекс и generated summaries не служат доказательством. Ответ опирается на прочитанный фрагмент с адресом и provenance.
2. По умолчанию читай адресные фрагменты и соблюдай бюджет `narrow`/`deep`. Не исполняй произвольный DataviewJS из заметок.
3. Сохраняй неизвестные поля, ручной текст, ссылки и раскладку Canvas. Существующий авторский prose меняй после явного `apply`/команды; managed blocks обновляй по ID. Повторный запуск не создаёт дублей.
4. MOC называется `MOC_<Название>.md`; HUB — парой `HUB_<Название>.md` и `HUB_<Название>.canvas`. У MOC один основной родитель, у статьи может быть несколько MOC.
5. Проверяй реальные возможности Obsidian/плагинов и границы доступа vault profile. Не выдавай `generated` за `executed` или `rendered`.
6. После каждой реально применённой записи vault заверши работу вызовом [`obsidian-index-sync`](docs/spec/skills/18-obsidian-index-sync.md): удалить прежние векторы изменённых файлов, полностью перестроить их RAPTOR-иерархию, для удалённых очистить индекс. При сбое сообщить `index_dirty`, не утверждать актуальность поиска.

## Новая функциональность или изменение поведения

1. Изучи репозиторий и существующие реализации. Найди user story, затронутые разделы/ID спецификации, ADR, алгоритмы и тесты; уточни фактический контракт.
2. Составь короткий [план](docs/planning.md): поведение, изменяемые интерфейсы/файлы, зависимости, риски, критерии проверки. Для существенного решения сначала запиши предлагаемые варианты и причину выбора.
3. Реализуй изменение в существующих слоях без параллельных адаптеров; проверь применимые сценарии из [руководства](docs/verification.md).
4. Обнови спецификацию до фактического поведения и уточни индексы, истории и алгоритмы. Новому требованию выдай код по [правилам](docs/spec/structure.md) и внеси его в реестр; старые ID не перенумеровывай. Если поведение намеренно отличается от требования, сначала оформи изменение требования.
5. Новое или пересмотренное архитектурное решение запиши отдельным `docs/adr/ADR-NNNN-*.md` по [шаблону](docs/adr/template.md): контекст, варианты, решение, причины, последствия. Добавь ссылку в [индекс ADR](docs/adr/index.md); старое решение пометь `Superseded`, не стирай историю.
6. После проверки оформи [описание результата в Git](docs/git-change-record.md): коммит с ID `US/REQ/LEG`, тем, что сделано, фактическими проверками и ограничениями; для pull request — сводку по всем коммитам. Если Git недоступен или коммит запрещён, подготовь текст и назови причину.
7. В итоговом сообщении укажи покрытые требования, проверки, ссылку/хеш Git-записи при наличии и оставшиеся ограничения. Не отмечай весь skill готовым по одному частному сценарию.
