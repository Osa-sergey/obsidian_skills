# Набор Claude Skills для тематического Obsidian Vault

Статус: спецификация для разработки, версия 0.8.0.
Дата: 2026-09-29.

Это описание будущего набора скиллов, а не установленная интеграция. Содержимое vault и установленные плагины не проверялись. Исторические вопросы и предварительные предложения в разделах 2–8 сохранены для трассировки; принятые рабочие дефолты приведены в §11. Правила кодирования новых требований и user stories — в §12.

## 1. Цель и границы

Превратить тематический vault в рабочую базу знаний, с которой Claude может последовательно выполнять поиск, собирать связанный контекст, проводить исследование и готовить согласованный набор новых статей, предложений по обновлению существующих материалов и навигационных страниц.

Под «статьёй» далее понимается Markdown-заметка в Obsidian. Под «источником» — как существующая заметка, так и исходная публикация, документ, запись или другой материал, на котором основано утверждение.

### Подтверждённые пользователем требования

- Искать заметки по названию через Omnisearch.
- Собирать списки связанных заметок по теме с задаваемой глубиной контекста.
- На основе исследования формировать новые статьи и предложения по изменению существующих статей близкой тематики.
- Сохранять ссылки на исходные данные и на статьи в vault.
- Собирать статьи в MOC; организовать сами MOC иерархически.
- В каждом MOC явно указывать ракурс рассмотрения темы отдельным полем.
- Представлять HUB как удобный для просмотра Canvas, объединяющий MOC и отдельные статьи, с этапами работы, изучения процесса или информации.
- Проставлять полезные перекрёстные ссылки и находить связи между Markdown-файлами.
- Формировать метаполя в YAML-заголовке, включая теги для поиска.
- Разделить функциональность на набор скиллов и уточнить вопросы по каждому.
- Поддержать два режима работы с базой знаний: `narrow` для точечных вопросов с минимальным контекстом и `deep` для исследования, синтеза и встраивания новых знаний.
- Добавить семантический поиск по иерархическому RAPTOR-представлению, построенному с учётом структуры Markdown: статья → раздел → подраздел → абзацы/чанки.
- Читать отдельные абзацы, разделы и при необходимости их подразделы без обязательного чтения статьи целиком.
- Объединять Omnisearch, поиск по терминам, RAPTOR, Dataview/Bases и граф связей в единый управляемый retrieval-процесс.
- Для каждого MOC хранить краткое summary и список основных терминов, используемых в карте.
- Для каждого HUB использовать обязательную пару: отдельная Markdown-заметка с описанием и связанный Canvas-файл.
- Новые статьи писать максимально структурированно: одна смысловая единица на абзац, явные заголовки/подзаголовки, устойчивые границы разделов для адресного чтения и RAPTOR-индексации.
- Поддерживать Obsidian Callouts вида `> [!TYPE]` для выделения определений, выводов, предупреждений, примеров, вопросов, источников и другой важной информации.
- Сохранять часто используемые Dataview/Bases-запросы как переиспользуемые файлы/представления внутри vault, снабжать их описанием назначения, условиями применения и ссылками из каталога запросов.

|---|---|---|---|

| 2 | `obsidian-context` | Обход существующих ссылок и графовых связей | Контекст по уровням, маршруты и причины отбора |

Скиллы 1–9 и 11–19 должны уметь работать самостоятельно в пределах своей ответственности. `obsidian-workflow` выбирает необходимые этапы для комплексного запроса. `obsidian-index-sync` дополнительно вызывается обязательно после любой применённой записи. Ключевой архитектурный принцип: специализированные поисковые адаптеры не отвечают на вопрос пользователя напрямую; они возвращают кандидатов и provenance, а `obsidian-retrieve` формирует общий retrieval-план и бюджет контекста.

## 2. Общая техническая основа

### 2.1. Скиллы и доступ к данным

Скилл определяет, как Claude выполняет задачу. Доступ к Obsidian обеспечивается отдельно: подключёнными инструментами, MCP, API или разрешённым чтением файлов.

Omnisearch документирует локальный HTTP-сервер для внешних запросов; его нужно включить. Он ранжирует результаты с учётом текста, имени файла и заголовков, поэтому нельзя автоматически считать все результаты поиском только по названию. Для режима поиска по названию адаптер должен проверить имя/заголовок найденной заметки и применить согласованные правила отбора. [S2]

Для чтения и изменения файлов можно рассмотреть Local REST API с MCP либо файловый доступ в локальном Claude Code. Local REST API документирует чтение, создание и изменение заметок, включая адресное обновление разделов и свойств. Поддержку именно Omnisearch в выбранном подключении следует проверить отдельно: наличие обычного поиска в MCP её не гарантирует. [S3]

Для первой реализации предлагается ориентироваться на локальный Claude Code, но это требует ответа на G1. В Claude Code скилл оформляется папкой с `SKILL.md`; описание помогает автоматическому выбору, а отдельный скилл можно вызвать по имени. Проектные скиллы размещаются в `.claude/skills/<имя>/SKILL.md`. [S1]

### 2.2. Общий профиль vault

Один согласованный профиль должен хранить:

- идентификатор vault, способ подключения и доступные возможности;
- разрешённые и исключённые папки;
- схему типов заметок, метаданных, тегов и алиасов;
- правила имён файлов и внутренних ссылок;
- словарь буквенных сокращений проектов/доменов для разрешения совпадений имён;
- обязательные префиксы навигационных файлов: `MOC_<Название>.md` для MOC и `HUB_<Название>.md` для Markdown-описания HUB; связанный Canvas именуется `HUB_<Название>.canvas`;
- места для новых статей, источников, MOC, HUB и исследовательских отчётов;
- лимиты поиска, обхода графа и объёма чтения;
- допустимые действия: отчёт, создание черновиков, применение выбранных изменений;
- правила обработки существующих пользовательских разделов.

Не следует копировать этот профиль целиком во все скиллы. Доступ к нему должен быть определён одинаково для всего набора. Ключи подключения хранить в конфигурации инструментов, а не в текстах статей.

### 2.3. Обязательные правила результата

1. Прочитать материал перед его содержательным использованием. Поисковый фрагмент служит для отбора, а не заменяет источник.
2. Различать обнаруженную заметку, прочитанный материал и материал, использованный для вывода.
3. Давать для существенного вывода ссылку на конкретное основание. Общего списка источников в конце недостаточно для спорных или точных утверждений.
4. Отделять факты источника, интерпретацию автора заметки и новый вывод Claude.
5. Не представлять ссылку на непрочитанный первоисточник как проверенное подтверждение. Если доступна только вторичная заметка, явно указывать это.
6. Разрешать внутренние ссылки до конкретного пути. Совпадение имён в разных папках и алиасы требуют проверки.
7. Не смешивать существующие ссылки и предлагаемые смысловые связи.
8. Искать существующее покрытие темы перед созданием статьи.
9. Для старых статей готовить адресные предложения изменений. Применять их только в рамках отдельного запроса на применение или заранее согласованного режима.
10. Сохранять чужие метаполя, авторские формулировки, ручные комментарии и разделы вне согласованной правки.
11. Повторный запуск на неизменившихся данных не должен плодить статьи, ссылки, теги и одинаковые предложения.
12. Перед записью сверять актуальную версию файла с прочитанной. При расхождении пересобрать правку, сохранив новые пользовательские изменения.
13. После любого реально применённого изменения содержимого vault завершить пакет вызовом [§3.18 `obsidian-index-sync`](skills/18-obsidian-index-sync.md). В отчёте отдельно показывать результат записи файлов и актуальность индекса (`REQ-RET-0001`).

### 2.4. Уточнённая модель: статьи, иерархические MOC и Canvas HUB

Уточнение пользователя от 2026-09-28 фиксирует три роли:

| Сущность | Назначение | Форма |
|---|---|---|
| Статья | Изложение конкретного материала; включается в MOC | Markdown-заметка |
| MOC | Подборка статей и дочерних MOC по теме в явно указанном ракурсе | Markdown-заметка с метаданными и аннотированными ссылками |
| HUB | Маршрут работы/изучения с машинно-читаемым описанием и визуальным представлением | Обязательная пара `HUB_<Название>.md` + `HUB_<Название>.canvas` |

Иерархия MOC, ракурс и маршрут HUB — разные отношения. Уровень MOC показывает положение в структуре темы. Ракурс объясняет, с какой стороны рассматривается тема. Положение на Canvas показывает роль материала в конкретном рабочем или учебном маршруте.

**Предлагаемые правила, требующие согласования деталей:**

- Для каждого MOC обязательны тема и явно заполненное поле `perspective` («ракурс»). Поле `perspective_question` поясняет, на какой вопрос отвечает этот взгляд. Например: `perspective: operations`, `perspective_question: Как поддерживать актуальность и надёжность RAG в эксплуатации?`.
- Возможные ракурсы: теория, архитектура, реализация, эксплуатация, оценка качества. Аудитория, сложность и позиция в процессе задаются отдельно: они не заменяют ракурс.
- Одна тема может иметь несколько MOC с разными ракурсами. Это разные подборки и объяснения, а не автоматически дублирующиеся заметки.
- Статью можно включать в несколько MOC ссылками, без копирования текста. Прямое включение статьи в HUB не отменяет её принадлежность MOC. Множественная принадлежность предлагается как базовое правило, окончательно уточняется в O9.
- Родительство хранить в `parent_mocs`. Корневой MOC имеет пустой список. До решения O7 предлагается один родитель; формат списка позволяет позже разрешить несколько родителей без смены типа свойства.
- Иерархия не допускает циклов. При нескольких родителях она становится направленным ациклическим графом. Перекрёстные тематические ссылки не считать отношением родительства.
- Дочерние MOC определять по `parent_mocs`; их аннотированный список в тексте родителя согласовывать с этими полями. Не хранить независимые несогласованные списки родителей и детей.
- В каждом MOC хранить ракурс явно, даже если он совпадает с родительским. Если дочерняя карта меняет ракурс, показывать это в её названии/аннотации и в переходе от родителя.
- Уровень иерархии вычислять по связям. При нескольких родителях указывать путь, относительно которого рассчитан уровень. Не смешивать его с глубиной обхода контекста и номером этапа HUB.
- Каждая итоговая статья должна иметь хотя бы один целевой MOC; для новых черновиков допустима запланированная принадлежность с явным статусом, пока MOC не создан.
- HUB выбирает необходимые материалы из разных уровней и ракурсов. Вся иерархия MOC не обязана помещаться на один Canvas.

**Устройство HUB:** визуальные группы представляют этапы. В каждой группе — название, цель, карточки нужных MOC/статей и ожидаемый результат этапа. Стрелки с подписями различают «следующий этап», «предпосылка», «альтернатива», «возврат на доработку». Порядок, зависимости и ветвления должны читаться без открытия всех карточек.

Пример: HUB «Разработка RAG» объединяет этапы постановки задачи, подготовки данных, реализации, оценки и эксплуатации. На этапе подготовки данных могут стоять MOC «Индексация — реализация» и отдельная статья «Чек-лист качества входных документов». На этапе оценки — MOC «RAG — оценка качества» и статья «Набор тестовых вопросов». Пример не задаёт обязательную структуру всех HUB.

Нативный Obsidian Canvas хранится в формате JSON Canvas и поддерживает карточки файлов, текст, группы и связи. Предлагается использовать карточки файлов для MOC и статей, а текстовые карточки — для кратких пояснений и легенды. [S6][S7]

Файл `.canvas` не является Markdown-заметкой с YAML. Поэтому для каждого HUB обязательна сопроводительная заметка `HUB_<Название>.md` с метаданными, summary, назначением, этапами, основными терминами и ссылкой на `HUB_<Название>.canvas`. Markdown-файл является машинно-читаемым описанием HUB и основной точкой поиска; Canvas отвечает за визуальный маршрут. Метаданные нельзя добавлять YAML-заголовком в JSON-файл. Линии Canvas и родительство MOC не считать автоматически одинаковыми связями. Текстовые карточки Canvas не появляются в Backlinks как самостоятельные заметки. [S6][S7]


### 2.5. Правила именования MOC и HUB

Для навигационных сущностей используются обязательные файловые префиксы, отделённые символом `_`:

- MOC: `MOC_<Название>.md`;
- Markdown-описание HUB: `HUB_<Название>.md`;
- Canvas HUB: `HUB_<Название>.canvas`.

Примеры:

```text
Maps/MOC_RAG - Индексация.md
Maps/MOC_GraphRAG - Эксплуатация.md
Hubs/HUB_Разработка RAG.md
Hubs/HUB_Разработка RAG.canvas
```

Префикс является частью имени файла и используется для быстрого распознавания типа заметки средствами файлового поиска, Omnisearch и автоматических skills. Поле `type` в YAML при этом остаётся обязательным источником семантического типа и не заменяется соглашением об имени файла.

При создании, переименовании и поиске MOC/HUB skills должны:

1. сохранять соответствующий префикс;
2. не создавать варианты `MOC - ...`, `HUB - ...` или файлы без префикса;
3. проверять, что Markdown-файл HUB и его Canvas имеют одинаковую базовую часть имени;
4. обновлять внутренние ссылки при согласованном переименовании;
5. не считать произвольный файл с похожим названием MOC/HUB без проверки YAML `type`.

**Глобальная уникальность (`REQ-FND-0001`).** Перед созданием или согласованным переименованием проверить имя файла не только в целевой папке, но и во всём доступном vault, а также среди файлов текущего пакета. Сравнивать нормализованные basename с расширением (Unicode NFC и casefold). Для нескольких материалов с одинаковым исходным названием в разных проектах добавлять перед названием согласованный буквенный код проекта/домена из vault profile: `RAG_Индексация.md`, `ML_Индексация.md`. Для навигационных файлов сохранять служебный префикс первым: `MOC_RAG_Индексация.md`, `HUB_ML_План.md` и парный `HUB_ML_План.canvas`. Код выбирать по единому словарю, не создавать разные сокращения одного проекта и не заменять его произвольной цифрой. Повторно проверить окончательные имена; при неразрешённом совпадении предложить новые варианты, не перезаписывать файл. Старые одноимённые заметки не переименовывать молча; их ссылки и векторы пока различать по полному пути. Для Canvas-пары одинаковый stem обязателен, расширения `.md` и `.canvas` делают имена файлов разными.

### 2.6. Два режима retrieval и иерархия RAPTOR

Система должна поддерживать два явно различимых режима.

**`narrow` — точечный ответ.** Используется для конкретного вопроса, поиска определения, алгоритма, факта, места в тексте или короткого списка. Цель — получить минимальный достаточный evidence set. По умолчанию нельзя читать статью целиком, если достаточно summary, конкретного раздела, подраздела или нескольких абзацев.

Для новых статей первая ступень просмотра тела — `## Суть` из двух предложений сразу после YAML (`REQ-KNO-0001`). Этот исходный фрагмент помогает решить, какие разделы читать дальше; старые заметки без него продолжают открываться обычным progressive retrieval. Metadata `summary` и RAPTOR summary используются для discovery, но не подменяют адресное чтение.

**`deep` — исследование и развитие базы.** Используется для обзора темы, сравнения подходов, поиска пробелов и противоречий, deep research, подготовки новых статей и встраивания новой информации. Режим допускает более широкий candidate set, несколько итераций поиска, обход MOC/графа и расширение выбранных RAPTOR-ветвей.

RAPTOR строится с учётом естественной структуры Markdown:

```text
article
└── section (H1/H2)
    └── subsection (H2/H3/...)
        └── paragraph group
            └── atomic paragraph/chunk
```

Для каждого индексируемого узла хранить как минимум: `path`, `heading_path`, `node_level`, `parent_id`, диапазон строк/абзацев, content hash, summary, embedding и список child IDs. Границы заголовков должны иметь приоритет над слепым token chunking. Если раздел слишком велик, он делится по абзацам/логическим блокам с сохранением обратной ссылки на исходный heading.

После записи vault узлы изменённого Markdown-файла строятся заново целиком через [§3.18 `obsidian-index-sync`](skills/18-obsidian-index-sync.md). Каждый vector payload содержит `source` (имя файла) и `source_path` (путь внутри vault); прежние vectors файла удаляются до записи новых (`REQ-RET-0001–0002`).

Прогрессивное раскрытие контекста:

1. metadata/MOC/HUB summary;
2. RAPTOR summaries верхнего уровня;
3. выбранные разделы и подразделы;
4. конкретные абзацы;
5. полная статья — только если без неё невозможно корректно выполнить задачу.

`obsidian-fragment-reader` является обязательным downstream-инструментом `obsidian-semantic-search`: семантический поиск возвращает адрес узла, reader читает исходный фрагмент и при необходимости раскрывает только его дочерние подразделы.

### 2.7. Hybrid retrieval и бюджет контекста

`obsidian-retrieve` объединяет независимые механизмы:

- Omnisearch — названия, текст и нечёткие совпадения;
- term search — точные термины, названия технологий, сущности и устойчивые фразы;
- RAPTOR — семантическое соответствие на уровнях article/section/subsection/chunk;
- Dataview/Bases — структурированные фильтры по свойствам, ссылкам, статусам и датам;
- MOC/HUB — навигационная близость, ракурс и место в тематической структуре;
- backlinks/outlinks — существующий граф заметок.

Dataview/Bases предпочтительно использовать как pre-filter, если вопрос содержит структурные ограничения. Например, сначала выбрать статьи `type=article`, `published>=2025`, относящиеся к RAG, и только затем выполнять RAPTOR по полученному scope.

Каждый запрос получает `context_budget`, например:

```yaml
mode: narrow
max_tokens: 6000
allocation:
  discovery: 800
  summaries: 1200
  evidence: 3200
  reserve: 800
```

Число файлов не является достаточным ограничителем. Оркестратор должен оценивать стоимость чтения summary/section/article и расширять контекст постепенно.


### Вопросы об окружении

- **G1 — критично.** Где будут запускаться скиллы: Claude Code локально, Claude Desktop/Cowork, веб-версия Claude или несколько сред?
- **G2 — критично.** Как подключён vault? Какие версии Obsidian, Omnisearch и инструменты доступа уже есть? Можно ли добавить недостающее подключение?
- **G3.** Один vault или несколько? Каков примерный размер: число заметок, общий объём, доля больших документов и вложений?
- **G4.** Какие плагины и соглашения нужно поддержать: Dataview/DataviewJS, Templater, Bases, собственные шаблоны? Какие из них обязательны?
- **G5 — критично.** Какие папки разрешено читать и куда можно создавать новые материалы? Какие папки исключить?
- **G6 — критично.** Какие действия разрешены сразу: только выдача черновиков, создание новых файлов, применение заранее описанных типов изменений? Предложения по существующим статьям считаем обязательным отдельным результатом.
- **G7.** Можно ли прислать 3–5 характерных заметок, один текущий MOC/HUB и дерево основных папок? Это позволит сохранить стиль и существующие соглашения.
