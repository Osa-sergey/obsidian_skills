## 3.18. `obsidian-index-sync` — обязательная синхронизация RAPTOR после записи

**Назначение:** после любого успешно применённого действия, которое добавило, изменило, удалило или переименовало содержимое vault, привести RAPTOR и векторный индекс в соответствие с текущими файлами. Самостоятельный вызов позволяет восстановить индекс для указанного набора путей. `answer`, `research` без записи и `prepare` без применения индекс не меняют.

**Обязательная точка вызова:** общий write coordinator/`obsidian-workflow` вызывает skill один раз в конце успешно применённого пакета изменений. Отдельные write skills (`author`, `revise`, `link`, `metadata`, `moc`, `hub`, `query-builder`, fragment editor и прямой разрешённый файловый adapter) передают события координатору; прямое действие также обязано завершиться index sync. Нельзя завершить запись с заявлением «индекс актуален», если sync не выполнен успешно. Для частично применённого пакета передаются только реально совершённые изменения. Изменение служебного состояния индекса само не инициирует новый вызов.

**Вход:** `vault_id`, `change_id`, список уникальных событий `created | modified | deleted | renamed` с `old_path`, `new_path`, типом файла и ожидаемым/фактическим content hash. Для rename нужны оба пути; для удаления достаточно старого пути и записанного в manifest идентификатора. События собираются до изменения файла и сверяются с фактическим результатом после него.

**Порядок работы:**

1. Привести пути к каноническим относительным путям vault, объединить повторные события по файлу и определить конечное состояние (`create→modify` = create, `create→delete` = no-op, rename хранит старый и новый путь). Для всех действительно затронутых файлов получить прежнюю идентичность индекса.
2. **Сначала удалить** из векторной БД все embeddings и RAPTOR-узлы, связанные с изменённым/удалённым файлом или старым путём переименованного файла, на всех уровнях `article/section/subsection/chunk`. Удалять по `vault_id + source_path` либо стабильному `file_uid`, а не по одному basename `source`, чтобы старые дубликаты не затронули соседний файл.
3. Для `deleted` после подтверждённого удаления векторов закончить обработку; исходный файл не читать и новые embeddings не строить.
4. Для `created`, `modified`, `renamed` прочитать актуальную версию файла и перестроить его иерархию целиком: Markdown — frontmatter → headings → paragraphs/callouts; `.canvas` — маршрут/группа → карточка/подпись; `.base` — представление → фильтры/поля. Эти структурированные текстовые форматы, которые создают skills набора, обязательно получают RAPTOR-узлы и embeddings. Для другого текстового файла адаптер выделяет разделы, если они есть, иначе создаёт корневой узел и смысловые блоки. Для бинарного вложения без доступного extractor результат — `not_indexable` с причиной и без старых векторов. Даже если изменился один абзац или узел Canvas, заменяется весь набор векторов файла.
5. Каждый новый вектор получает payload: `vault_id`, `source` (**имя файла с расширением**), `source_path` (канонический путь внутри vault), `file_uid` при наличии, `content_hash`, `node_id`, `node_level`, `heading_path`, диапазон исходного текста и `parent_id`. `source` позволяет найти все векторы по названию; `source_path` остаётся точным ключом удаления и различения legacy файлов.
6. Сверить актуальный hash, число записанных узлов и отсутствие старых векторов по прежнему пути. Сохранить состояние sync по `change_id` и ответить только после проверки. Повторный вызов с тем же конечным hash не создаёт дубли.

**Ошибки и восстановление:** если удаление/запись в БД не завершились, пометить файл `index_dirty`, сохранить операцию для повтора и явно сообщить, что поиск по нему может быть неполным. При следующем вызове повторить full replacement; не объявлять действие с vault откатанным только из-за сбоя индекса. Пока `index_dirty`, semantic search не выдаёт устаревшие векторы за актуальные и может открыть исходный Markdown через fallback. Для переименования удаляются записи старого пути даже при отсутствии файла по этому пути.

**Миграция старого индекса:** если существующие векторы не имеют `source_path` или `source`, фильтр точного удаления недостоверен. До использования нового контракта выполнить одноразовую полную очистку и перестроение индекса доступных файлов vault с новым payload; до завершения помечать semantic index неготовым. Не пытаться удалить legacy-дубликаты одним только `source`.

**Выход:** `IndexSyncResult`: `change_id`, обработанные пути/операции, удалённые/записанные узлы, hash, `indexed | deleted | not_indexable | index_dirty`, ошибки и возможность повторить. Результат включается в отчёт исходной write-операции.

**Критерии приёмки:** `AC-REQ-RET-0001-01/02`, `AC-REQ-RET-0002-01/02` в [реестре](../requirements-registry.md); сценарии — в [проверке](../../verification.md). Это описание будущего skill, а не утверждение о его реализации.
