## 4. Предлагаемая схема метаданных

### 4.1. Статьи

Обязательное ядро для обсуждения: `type`, `status`, `tags`, `created`, `updated`. `aliases` и `summary` полезны, но могут быть опциональными. Перед внедрением схему нужно сверить с текущими свойствами vault; значения ниже — иллюстрация, а не миграция существующих файлов.

Пример для новой статьи; все названия заметок условные:

```yaml
---
type: concept
status: draft
tags:
  - rag/graph
  - rag/updates
aliases:
  - Incremental GraphRAG
summary: Подходы к обновлению графового индекса при изменении документов.
created: 2026-09-28
updated: 2026-09-28
topics:
  - "[[Topics/GraphRAG]]"
sources:
  - "[[Sources/Исходная публикация об обновлении графа]]"
moc:
  - "[[Maps/MOC_Обновление GraphRAG]]"
hub:
  - "[[Hubs/HUB_RAG и системы знаний.canvas]]"
---
```

| Поле | Тип | Назначение |
|---|---|---|
| `type` | Текст | Роль заметки |
| `status` | Текст | Стадия работы с заметкой |
| `tags` | Список тегов | Фильтрация и классификация |
| `aliases` | Список | Альтернативные имена |
| `summary` | Текст | Краткое содержание |
| `created`, `updated` | Дата | Создание и содержательное изменение |
| `topics` | Список ссылок | Сущности или тематические заметки |
| `sources` | Список ссылок/URL | Основания статьи в целом |
| `moc`, `hub` | Списки ссылок | Навигационная принадлежность |

В YAML внутренние ссылки следует заключать в кавычки. `tags` — специальное свойство Obsidian; произвольные свойства вроде `topics` и `status` не становятся тегами автоматически. По ним используют поиск по свойствам или запросы выбранного плагина. [S4]

Дополнительные поля вводятся под конкретную потребность: для источника — `source_url`, `authors`, `published`, `accessed`; для учебной статьи — `difficulty`, `prerequisites`; для регулярной проверки — `reviewed`. Не добавлять их ко всем заметкам без пользы для поиска и работы.

Для **новой статьи** сразу после YAML обязателен видимый раздел из двух предложений (`REQ-KNO-0001`):

```markdown
## Суть

Инкрементальное обновление GraphRAG изменяет затронутые узлы и связи графа после появления новых документов. Такой подход сокращает объём пересборки, но требует контроля согласованности индекса и исходных данных.

## Как это работает

...
```

`summary` в YAML — свойство для фильтрации и карточек; раздел `## Суть` — первый адресуемый фрагмент тела для читателя и fragment reader. Существующие статьи не переписываются автоматически ради добавления раздела. Имя новой статьи проходит глобальную проверку по [`REQ-FND-0001`](foundation.md#25-правила-именования-moc-и-hub).

**Payload векторного индекса (`REQ-RET-0002`):** каждый RAPTOR-узел имеет `source` (имя файла с расширением), `source_path` (канонический путь внутри vault), `vault_id`, `content_hash`, `node_id`, `node_level`, `heading_path` и исходный диапазон. `source` предназначен для поиска по имени; точное удаление использует vault + `source_path`/`file_uid`, особенно для старых совпадающих названий. Это metadata векторной БД, а не новое YAML-поле статьи.

`created` сохраняется при редактировании. `updated` меняется при реальном содержательном обновлении, а не при каждом запуске скилла. Внешняя дата публикации и дата создания локальной заметки — разные данные.

Список `sources` помогает навигации, но точные утверждения всё равно должны иметь основания в теле заметки. Формат внутренних ссылок может включать статью, её заголовок или блок: `[[Путь/Статья]]`, `[[Путь/Статья#Раздел]]`, `[[Путь/Статья#^block-id]]`. Проверять существование адресата и не добавлять block-id в чужую статью без предусмотренного изменения. [S5]

### 4.2. MOC: тема, ракурс и родительство

Имена полей — предложение. Все ссылки в примере условные:

```yaml
---
type: moc
status: draft
topics:
  - "[[Topics/Индексация RAG]]"
perspective: operations
perspective_question: Как обновлять индекс без потери актуальности и доступности?
summary: Карта практик обновления RAG-индекса в эксплуатации: инкрементальные изменения, переиндексация, консистентность и контроль актуальности.
terms:
  - incremental indexing
  - reindex
  - freshness
  - consistency
  - GraphRAG
parent_mocs:
  - "[[Maps/MOC_RAG - Эксплуатация]]"
tags:
  - rag/indexing
  - perspective/operations
created: 2026-09-28
updated: 2026-09-28
---
```

В начале тела MOC обязательны секции `## Summary` и `## Основные термины`. Summary — 1–3 компактных абзаца о том, что покрывает MOC и чем этот ракурс отличается от соседних. Основные термины — короткий список ключевых терминов, синонимов, английских/русских вариантов и устойчивых названий технологий, используемый быстрым lexical/term retrieval. Далее показать родителя, дочерние MOC и статьи с аннотациями. `perspective` отвечает за ракурс и фильтрацию, `perspective_question` — за его конкретный смысл. Тег ракурса опционален; при его использовании проверять соответствие основному полю.

`parent_mocs` — источник родительства; видимые списки дочерних карт выводятся/обновляются по нему. Поле `moc` у статьи хранит прямую принадлежность; аннотированные списки статей в MOC должны с ней согласовываться. При расхождении существующих данных показать конфликт и предложить исправление, а не автоматически удалять вручную выбранные статьи.

### 4.3. HUB: обязательная пара Markdown-описание + Canvas

Для схемы с сопроводительной Markdown-заметкой предлагаются:

```yaml
---
type: hub
status: draft
purpose: Пройти этапы разработки и проверки RAG для документов.
summary: Маршрут от постановки задачи и подготовки данных до retrieval, evaluation и эксплуатации.
terms:
  - RAG
  - retrieval
  - indexing
  - evaluation
  - operations
route_type: workflow
canvas: "[[Hubs/HUB_Разработка RAG.canvas]]"
tags:
  - rag
  - navigation/hub
created: 2026-09-28
updated: 2026-09-28
---
```

`route_type` может быть `workflow` или `learning` как согласованный словарь. Несколько маршрутов могут использовать одни и те же MOC/статьи. Позиция статьи в конкретном HUB хранится на стороне маршрута/Canvas и не задаётся глобальным `stage` в статье: в другом HUB эта статья может выполнять другую роль.

Markdown-файл HUB является обязательным и должен содержать минимум:

```markdown
# HUB — <Название>

## Summary
Краткое описание назначения и границ маршрута.

## Основные термины
- ...

## Этапы
### 1. ...
Цель, входы, ключевые MOC/статьи, ожидаемый результат.

## Ветвления и альтернативы
...

## Связанный Canvas
![[HUB_<Название>.canvas]]
```

Canvas остаётся самостоятельным JSON-файлом. Для поиска маршрутов и чтения контекста в первую очередь используется Markdown-описание; чтение `.canvas` необходимо для геометрии, визуальных групп и рёбер. Отсутствие такой возможности нельзя скрывать под обычным поиском Markdown.


### 4.4. Реестр Dataview/Bases и поисковых представлений

Рекомендуемая папка: `System/Queries/`. Это часть базы знаний, а не внутреннее состояние Claude.

Минимальные типы артефактов:

- `.base` — сохраняемые интерактивные выборки;
- `.md` с DQL — документированный Dataview-запрос и пример результата;
- `.js`/view — только для согласованных DataviewJS data adapters;
- `README.md` — индекс всех сохранённых запросов.

Пример записи в каталоге:

```markdown
### Articles without MOC
- **Engine:** Dataview DQL
- **Use when:** нужно найти статьи, ещё не встроенные в структуру MOC
- **Do not use when:** нужно искать семантическое содержание статей
- **Requires:** `type`, `moc`
- **Definition:** [[System/Queries/Dataview/Articles without MOC]]
- **Used by:** [[MOC_Knowledge maintenance]]
- **Status:** executed
```

Ссылки на сохранённые запросы могут храниться в MOC/HUB, если они являются частью пользовательского представления. Retrieval-слой использует реестр как библиотеку воспроизводимых структурных pre-filter'ов.
