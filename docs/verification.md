# Проверка изменений

Сначала выясни реальные команды проекта из README, manifests и CI. Проверяй затронутое поведение; не утверждай успешность недоступной интеграции.

## Retrieval и ответ

- Кандидат и evidence различаются; цитируемый fragment действительно прочитан из актуального Markdown.
- Узкий вопрос читает подраздел/абзац; бюджет и early stop соблюдаются.
- Аббревиатуры, дубликаты имён и циклы графа не подменяют адреса; discovered relation не записывается как existing edge.
- При недоступном Omnisearch есть обозначенный fallback; при stale RAPTOR address выполняется перепроверка.
- Противоречие показано, независимость первоисточников проверена.

## Запись и структура

- `prepare` выдаёт reviewable diff; `apply` проверяет свежесть файла, меняет только разрешённое и повторяется без дублей.
- Неизвестные YAML-поля, ручной текст и чужие managed blocks сохраняются.
- MOC: имя, `type`, ракурс, summary/terms, один parent, отсутствие циклов.
- HUB: парные имена, валидный Canvas, существующие targets, прежние IDs/координаты и ручные nodes.

## Запросы

- Definition соответствует движку, параметрам и scope; реестр указывает условия применения.
- Неизвестный DataviewJS не исполняется; статический preview не выдаётся за рендер в Obsidian.
- Повторная вставка managed block обновляет ID, а не добавляет второй блок.

## Пробелы и внешний поиск

- С подсказкой о GraphRAG проверить её по HUB и соседним заметкам, включая синонимы и адресные фрагменты; учесть частичное покрытие и ограничения scope.
- Без подсказки выявить значимый для цели HUB пробел, а не просто отсутствующее слово; при грязном индексе не утверждать полноту анализа.
- Запросы различаются по исследовательским вопросам, имеют цель, язык, тип ожидаемого источника и критерий остановки. Имя автора встречается только при адресном подтверждении в прочитанной заметке; статус `planned` не выдаётся за проведённый поиск.

## Запись vault и актуальность индекса

- Каждый успешно применённый пакет create/modify/delete/rename завершает один вызов `obsidian-index-sync` с фактическим change set; `prepare` без записи не вызывает его.
- До записи новых vectors удалены все старые по точному `vault_id + source_path`; `source` хранит имя файла, соседние legacy-файлы с тем же basename не затронуты.
- Изменённый Markdown заново разбит по разделам целиком; `.canvas` и `.base` структурно разобраны их адаптерами; удалённый только очищен; rename очищает старый путь. Бинарное вложение без extractor явно получает `not_indexable`. Повторение не создаёт дубли.
- Сбой даёт `index_dirty` и повторяемый результат; semantic search не использует устаревшие vectors как актуальные.
- Новые имена проверены глобально, проектные буквенные префиксы согласованы; новая статья имеет двухпредложный `## Суть`, а запрос папки возвращает полный список с контролем scope.

## Документация и завершение

После реализации сверить изменённое поведение с затронутыми паспортами, картами и алгоритмами; при новом архитектурном выборе — ADR и его индекс. В [Git-записи результата](git-change-record.md) назвать релевантные ID, команды/fixtures, реальные результаты и конкретные непроверенные интеграции. Полные сценарии — в [§7 спецификации](spec/acceptance.md).
