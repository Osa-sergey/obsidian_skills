# Основные алгоритмы

Это инженерное описание последовательности, а не самостоятельный источник требований. При изменении шага найди нормативный файл через [индекс спецификации](spec/index.md) и обнови его, затем этот файл.

## 1. Поиск и ответ

**Вход:** вопрос, `mode`, scope/filters, `context_budget`. **Выход:** ответ и evidence set либо явно обозначенный пробел.

1. Разобрать вопрос на проверяемые части; определить `narrow` или `deep`. Структурные фильтры применить до семантического поиска, если они заданы.
2. Найти кандидатов через Omnisearch, точные термины, RAPTOR, saved Dataview/Bases views и релевантные MOC/HUB. При недоступности одного движка использовать обозначенный fallback и сообщить о потерянном покрытии.
3. Объединить кандидатов по каноническому пути и адресу фрагмента. Для каждого сохранить способ нахождения, версию и причину релевантности; не превращать предполагаемые отношения в ссылки графа.
4. Расширить существующие backlinks/outlinks в пределах бюджета. Прочитать только нужные исходные разделы/абзацы через fragment reader; зависимое определение запросить отдельным адресным чтением.
5. Построить `claim → evidence`: путь, heading, диапазон/стабильный ID, тип подтверждения, независимость первоисточника. Для противоречия сохранить обе позиции.
6. Остановиться при достаточном прямом evidence; в `deep` провести второй прицельный проход, только если он меняет вывод или закрывает пробел. Сформировать ответ с основаниями, не ссылаясь на непрочитанные результаты.

**Ошибка/граница:** stale RAPTOR address → перечитать Markdown, пересчитать адрес/индекс; исчерпан бюджет → обозначить непроверенные части. См. [retrieval](retrieval-map.md), [ADR-0001](adr/ADR-0001-retrieval.md).

## 2. Индексация Markdown и fragment reader

**Вход:** путь и содержимое исходной заметки, прежние hashes. **Выход:** дерево узлов с разрешимыми адресами.

1. Разобрать frontmatter, заголовки, абзацы и callouts; сохранить `path`, `heading_path`, диапазоны, parent/child IDs и content hash. Не смешивать соседние разделы ради фиксированного размера chunk.
2. После фактической записи получить change set. Для каждого изменённого/переименованного файла сначала удалить **все** старые RAPTOR-узлы и embeddings по `vault_id + source_path` (для rename — по старому пути), затем заново построить все уровни и summaries файла: Markdown по заголовкам, Canvas по маршруту/группам/карточкам, Bases по представлениям/полям. Для удалённого — только очистить прежние векторы. Неизменённые файлы не трогать.
3. Embedding строить над заново полученными узлами; каждый vector payload снабдить `source` (имя файла), `source_path` (точный vault-relative путь), node address и hash. При чтении сверять текущий hash и возвращать точный fragment, по запросу с дочерними подразделами. Полный файл — последняя ступень.
4. Callout оставлять отдельным leaf с типом и родительским heading. Generated summary допустим для discovery, но evidence требует исходного текста.

**Состояния reader:** `resolved`, `needs_context`, `stale_address`, `not_found`, `out_of_scope`. Точные интерфейсы закрепить в паспорте skill при реализации. См. §2.6 и §3.13–3.16 спецификации.

Выполнить [§3.18 index sync](spec/skills/18-obsidian-index-sync.md) один раз после каждого применённого пакета изменений vault; для сбоя оставить `index_dirty` и повторяемую операцию, не объявлять поиск актуальным. Для новой статьи первым дешёвым чтением тела служит двухпредложный `## Суть`; старые статьи могут его не иметь.

## 3. Создание и обновление знаний

**Вход:** подтверждённые findings и scope записи. **Выход:** draft/patch, применённые изменения и change manifest.

1. Найти существующие статьи по semantic core. Решить `update` или `new`: отдельная цель/ракурс/уровень оправдывают новый файл. До create/rename проверить глобальную уникальность basename и согласованный буквенный префикс проекта.
2. Подготовить структурированный Markdown и точные ссылки на основания. Для существующего prose составить адресный patch; для managed block использовать его стабильный ID.
3. В `prepare` вывести diff и dependencies. В `apply` перечитать текущий файл, проверить hash/контекст patch, обновить только разрешённые области атомарно; при конфликте пересобрать предложение.
4. Обновить links/YAML аддитивно. Не дублировать ссылки, теги и черновики на повторном запуске. Связи без существующего edge помечать как proposals.
5. Изменить MOC при изменении тематического каталога; HUB — только если меняется маршрут. Собрать фактические create/modify/delete/rename события и обязательно вызвать `obsidian-index-sync` в конце пакета. Записать change ID, проверку ссылок, статус индекса и результат в manifest.

**Ошибка/граница:** неизвестное поле или ручной блок сохраняется; merge/split/rename/delete существующего файла остаются proposal до отдельной команды. См. [ADR-0002](adr/ADR-0002-writes.md).

## 4. MOC и HUB

MOC: проверить `MOC_`, `type`, summary, terms, perspective; добавить curated static links с аннотациями; динамический view держать отдельно. `parent_mocs` содержит не более одного основного родителя, `related_mocs` — поперечные связи. Перед записью проверить цикл.

HUB: создать/обновить парные `HUB_<Имя>.md/.canvas`, проверить одинаковую основу имени и ссылки. Изменять Canvas по стабильным node IDs: сохранить координаты и ручные карточки, добавить новые элементы рядом с соответствующим stage; full relayout только по явной команде. Проверить валидность JSON Canvas и все target paths. См. [ADR-0003](adr/ADR-0003-navigation.md).

## 5. Запросы Dataview/Bases

1. Найти reusable definition в `System/Queries/README.md`; уточнить scope и параметры (явный вызов → YAML заметки → defaults).
2. Выбрать engine: Bases для сохраняемого представления, Dataview для гибкой выборки; DataviewJS выполнять лишь в классифицированном data-only контракте. Не исполнять неизвестные side effects.
3. Построить/проверить запрос в sandbox или target note. Отдельно зафиксировать `generated`, `executed`, `rendered`; без открытого Obsidian view нельзя утверждать последнее.
4. Для reusable запроса сохранить definition, параметры, условия применения и запись каталога. При вставке оградить managed block стабильным ID, перечитать target и не дублировать блок. В `deep` сохранить snapshot с датой и путями результатов.

См. §3.11–3.12, §4.4, §10–11 спецификации и [ADR-0004](adr/ADR-0004-query-views.md).

## 6. Анализ пробелов и план внешнего поиска

**Вход:** HUB/MOC/тема, необязательная подсказка, цель исследования и scope. **Выход:** `CoverageGap[]` и `ExternalSearchQueryPlan`, без автоматической записи vault.

1. Прочитать summary и структуру HUB/MOC, затем собрать связанные заметки и ближайшие источники через deep retrieval. Сначала `## Суть`, затем релевантные исходные разделы. При грязном индексе обратиться к Markdown и обозначить ограничение охвата.
2. С подсказкой проверить указанную тему по синонимам и соседним разделам; без неё сопоставить цель и этапы HUB с фактическим покрытием ключевых вопросов. Для каждого кандидата сохранить прочитанные адреса, частичное покрытие, недостающее знание, тип и неопределённость.
3. Отобрать существенные пробелы, разложить их на проверяемые исследовательские вопросы. Составить ранжированные RU/EN запросы по разным ракурсам и типам источников; персональные запросы — только для автора, чьё имя найдено в прочитанном фрагменте.
4. Вернуть тексты запросов, цель каждого, ожидаемый тип результата и критерий остановки. Если найдено достаточное внутреннее покрытие, сказать об этом и сократить план. Сохранить статус `planned`; исполнение и проверка внешних источников передаются `obsidian-research` по задаче пользователя.

См. [§3.19](spec/skills/19-obsidian-gap-search.md), [формат §5](spec/result-formats.md) и [ADR-0007](adr/ADR-0007-gap-search.md). Dataview/Bases запросы остаются в [§5 этого файла](#5-запросы-dataviewbases).
