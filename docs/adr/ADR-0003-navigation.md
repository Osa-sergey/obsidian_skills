# ADR-0003 — Иерархический MOC и парный HUB

- Статус: Accepted
- Дата: 2026-09-29
- Связанные требования: [основа §2.4–2.5](../spec/foundation.md), [MOC §3.8](../spec/skills/08-obsidian-moc.md), [HUB §3.9](../spec/skills/09-obsidian-hub.md), [модель §4](../spec/data-model.md), [дефолты §11](../spec/defaults.md) (O, H)

## Контекст

Нужны тематические карты по ракурсу и визуальные маршруты с этапами. Для поиска и машинного чтения Canvas недостаточно удобен как единственный носитель описания. Множественное родительство усложняет дерево и проверку циклов.

## Варианты

1. Неограниченный DAG MOC — гибок, но сложно объяснить основное положение карты и поддерживать дерево.
2. Canvas-only HUB — удобен визуально, хуже для текстового discovery.
3. Один основной parent MOC, дополнительные relations отдельно, HUB как Markdown + Canvas — выбранный вариант.

## Решение и причины

`parent_mocs` хранит 0 или 1 основного родителя; `related_mocs` — дополнительные связи. Статья может ссылаться из нескольких MOC без копирования. `HUB_<Имя>.md` описывает purpose/stages/terms и ссылается на парный `HUB_<Имя>.canvas`; последний показывает маршрут. Префиксы `MOC_`/`HUB_` позволяют находить файлы, YAML `type` подтверждает смысл. При обновлении Canvas сохраняются ручные координаты и ID.

## Последствия и пересмотр

Нужны проверка циклов, соответствия пары и миграционные proposals для старых имён; схема `parent_mocs` остаётся списком для совместимости с ранее описанной структурой. Если реальные сценарии потребуют нескольких равноправных родителей, пересмотреть дерево отдельным ADR и планом миграции.
