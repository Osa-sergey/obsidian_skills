# Планирование изменений

План нужен перед новой функциональностью, изменением контракта или затрагиванием нескольких skills. Для маленькой локальной правки достаточно короткого плана в задаче; этот файл не вводит отдельный постоянный трекер прогресса.

## Как составить план

1. Найти [user story](spec/user-stories.md) и сформулировать один наблюдаемый результат: вход, выход и режим (`answer`, `research`, `prepare`, `apply`).
2. Найти разделы/ID спецификации по [карте](index.md), действующие ADR и фактический код. Для новой нормы получить ID по [правилам](spec/structure.md) и записать в [реестр](spec/requirements-registry.md). Назвать неизвестные свойства окружения; проверить их до выбора адаптера.
3. Нарисовать границу изменения: затронутые skills, форматы данных, сторонние вызовы, хранилища, файлы vault и вызывающие компоненты. Отметить обратную совместимость и миграцию, если меняется persisted формат.
4. Разбить работу на небольшие проверяемые шаги: контракт → реализация → интеграция → проверка → синхронизация документации → [Git-запись результата](git-change-record.md). У каждого шага критерий готовности.
5. Для существенного выбора выписать 2–3 реальных варианта и причины выбора; подготовить ADR. Если решение меняет требование, обновить спецификацию до или вместе с кодом.
6. Перечислить негативные сценарии: недоступный плагин, stale index, конкурентная правка файла, повторный запуск, конфликт metadata, превышенный budget. Выбрать только проверки, относящиеся к изменению.

## Короткий шаблон задачи

```markdown
### Цель и сценарий
Вход → ожидаемый наблюдаемый результат.

### Основание
US, `LEG-*`/`REQ-*`, разделы спецификации; ADR; найденная реализация и фактические возможности.

### Изменение
Контракты/файлы/адаптеры; зависимости и миграция; границы записи.

### Шаги
1. ... (проверяемый результат)
2. ...

### Проверка
Нормальный случай; важный сбой/повтор; интеграция; что нельзя проверить локально.

### Документация
Спецификация; алгоритм; карта; ADR и его индекс при архитектурном решении.

### Git-запись
Какие US/REQ/LEG включить в сообщение коммита; что отразить в PR при нескольких коммитах.
```

План не заменяет исследование кода и не обязывает читать всё ТЗ. При неожиданном ограничении пересмотри границу и зафиксируй причину изменения плана.
