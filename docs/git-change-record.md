# Описание результата в Git

После реализации и проверок зафиксируй результат в истории Git. Используй commit message для одной законченной задачи; если работа оформляется pull request, его описание объединяет результаты всех входящих коммитов. Запись должна помогать восстановить связь `US/REQ/LEG → изменение → проверка` без чтения переписки.

## Перед записью

1. Посмотри `git status` и diff; включай в коммит только файлы текущей задачи. Не коммить чужие изменения и секреты.
2. Убедись, что спецификация, индексы, алгоритмы, ADR и тесты обновлены в пределах изменения. Не отмечай непроверенный skill завершённым.
3. Укажи только фактически запущенные проверки и их результат. Если часть проверки недоступна, назови причину.

## Формат сообщения коммита

```text
<тип>: <краткий наблюдаемый результат> [US-XXX] [REQ-...]

Что сделано:
- Изменены <поведение/контракт/файлы>.

Основание:
- <US и REQ/LEG, при необходимости ADR>.

Проверено:
- <команда или сценарий> — <результат>.

Ограничения:
- <что осталось или не проверено; «нет» при полном покрытии задачи>.
```

`<тип>` выбирай по существующему соглашению репозитория; если его нет, используй понятное `feat`, `fix` или `docs`. Не добавляй ID, не относящиеся к изменению. Для pull request добавь краткий план миграции/отката, если меняются сохранённые данные или контракт между skills.

Если работа выполняется вне Git или коммитить нельзя по явной инструкции, подготовь этот текст в итоговом сообщении и прямо укажи, что запись в Git не создана. Не создавай отдельный журнал прогресса ради дублирования истории коммитов.
